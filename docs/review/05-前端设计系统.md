## A. 两套视觉系统在一次点击内切换

### 问题

**总览页 = 暖色拟物**，token 全部取自反编译的 ARGB 常量（`app.css:57-105`）：

```css
--text:#723900;    /* 主文字：深棕（官方 #FF723900，出现 11 次） */
--sub:#9A7A4A;     /* 次级文字 */
--card:#F9EFDE;    /* 卡片底（官方 #F9EFDE） */
--accent:#FF990F;  /* 主强调橙（官方 #FF990F） */
```

**内页 = iOS 系统色**，且**完全不引用**上面这组 token：

| 行号 | 声明 |
| --- | --- |
| `app.css:1621-1622` | `main section[data-page]:not([data-page="main"]){ background:#F2F2F7 }` |
| `app.css:1113` | `.form .frow{ border-top:1px solid #F0F0F2 }` |
| `app.css:1117` | `.form .k{ color:#1C1C1E }` |
| `app.css:1118` | `.form .u{ color:#8A8A8E }` |
| `app.css:1559` | `background:#F2F2F7`（又一处） |
| `app.css:1652` 附近 | `.pgsec-t{ color:#8A8A8E }` |

`#F2F2F7` / `#1C1C1E` / `#8A8A8E` / `#F0F0F2` 是 iOS 的 systemGray6 / label / secondaryLabel / separator。

**根因**：官方 QQ 宠物的首页与设置页本来就是两种风格，项目照抄了两者，却没做**过渡**。用户从暖黄橙的总览点进设置，一次点击内视觉体系整个换掉。

### 修复

**为内页建立第二组 token**，全部改引用该组，**禁止裸色值**：

```css
/* :root 内新增 —— 内页（系统设置风） */
--sys-bg:#F2F2F7;        /* 页面底 */
--sys-card:#FFFFFF;      /* 卡片底 */
--sys-sep:#F0F0F2;       /* 分隔线 */
--sys-text:#1C1C1E;      /* 主文字 */
--sys-sub:#8A8A8E;       /* 次级文字 */
--sys-accent:var(--accent);   /* 强调色沿用暖橙，作为两套体系的唯一连接点 */
```

改引用清单（`grep -n` 逐条替换）：

```bash
grep -n '#F2F2F7\|#1C1C1E\|#8A8A8E\|#F0F0F2' web/src/styles/app.css
```

替换规则：

| 裸色值 | 改为 |
| --- | --- |
| `#F2F2F7` | `var(--sys-bg)` |
| `#FFFFFF`（内页上下文） | `var(--sys-card)` |
| `#F0F0F2` | `var(--sys-sep)` |
| `#1C1C1E` | `var(--sys-text)` |
| `#8A8A8E` | `var(--sys-sub)` |

**过渡处理**：`app.css:209-211` 已有 320ms 的转场动画。在转场时把顶栏底色从房间采样色渐变到 `--sys-bg`，让"换系统"这件事被视觉解释，而不是突兀跳变。

### 影响面与风险

- 内页是全站最大的一块（`.form` / `.cfg` / `.pgsec` / `.plan*` 全家），改动面广。**建议按 section 分批**，每批一次真机截图。
- `prefers-color-scheme:dark`（`app.css:1502-1518`）**只换背景图 token，不动任何颜色**（这是刻意的，官方没有独立深色主题）。新增 `--sys-*` 后要确认深色模式下的内页行为不变 —— 即 `--sys-*` **不参与**深色切换。

### 验收标准

```bash
# 裸色值清零（内页相关）
grep -c '#F2F2F7\|#1C1C1E\|#8A8A8E\|#F0F0F2' web/src/styles/app.css   # 期望 0
```

1. 真机（iOS + Android）从总览点进设置、日志、通知、冒险、职业五页，确认底色/文字色一致。
2. 深色模式切换后内页行为与改动前一致。
3. 转场过程中无闪烁。

### 回归风险点

- `FRONTEND_PITFALLS.md` 第 4 节：改 CSS 前先 `grep` 有没有 `@media` 里的同名规则。
- 若把 `--sys-*` 加进 `prefers-color-scheme:dark` 段，会破坏"官方没有深色主题"这一决策 —— **不要加**。

## B. 材质与功能层级反置

### 问题

项目有三档材质（`app.css:72-105`）：

| token | 值 | 用在哪 |
| --- | --- | --- |
| `--mask-black` / `--btn-r-bg` | `rgba(0,0,0,.28)` | **右列圆钮** |
| `--panel-bg` | `rgba(255,255,255,.62)` | 任务卡、底栏、功能栏 |
| `--panel-bg-strong` | `rgba(255,255,255,.80)` | 资料卡、左列圆钮 |

关键在注释（`app.css:288-293`）：

> 底色是官方那层纯黑蒙版（`--btn-r-bg`，与白玻璃面板**故意不同**）

以及 `app.css:104`：

> 任务卡 `.qpanel` / 底栏 `.deck` 仍走 `--panel-bg`，右侧圆钮仍是 `--btn-r-bg` 黑蒙版。

**但右列三颗圆钮早已不是装饰钮** —— `Overview.tsx` 里它们分别指向冒险、职业、实时画面三个**真实页面**。而左列四颗（设置/日志/通知/换背景）用了更亮的 `--panel-bg-strong`。

**结果：最需要被看见的功能入口，用了最暗的材质。** 同屏 4 种材质并存。

### 修复

材质收敛为**两档**，按"功能 vs 装饰"而非"左 vs 右"划分：

```css
/* 两档材质：面板（承载内容）/ 入口（可点） */
--panel-bg:rgba(255,255,255,.62);         /* 内容面板：任务卡、底栏、功能栏、资料卡 */
--entry-bg:rgba(255,255,255,.80);         /* 可点入口：左右两列圆钮统一 */

/* 废弃 */
/* --btn-r-bg / --mask-black 不再用于圆钮；黑蒙版仅保留给胶囊条（--cap-bg） */
```

改动点：`app.css` 中 `.col-r .rbtn` 的 `background:var(--btn-r-bg)` → `var(--entry-bg)`。

层级差异改用**图标色**区分（左列棕 `--btn-l-fg:#BE6321` 系统入口 / 右列暖黄 内容入口），而不是靠亮度。

### 影响面与风险

- 右列圆钮变亮后，白色图标需要换成深色图标（否则对比度不足）。`Overview.tsx:97-99` 的 SVG 引用处要一并处理。
- `app.css:264-266` 的注释记录了"用户要求圆钮背景跟资料卡一样"——**这次改动与用户既有偏好方向一致**（让右侧也跟资料卡一样），但要确认不是反过来的意思。

### 验收标准

1. 截图对比：右列三颗圆钮与左列四颗材质一致。
2. 全屏只有 2 种面板材质（胶囊条除外）。
3. 圆钮图标在明亮背景下清晰可辨（对比度 ≥ 3:1，图标属大图形）。

### 回归风险点

- `Overview.tsx` 里圆钮图标是 `/qp-icons/ctrl/*.svg`，若 SVG 自带白色 fill，改材质后会看不见 —— 用 `filter: brightness(0) saturate(100%) ...` 或换图标文件。

## C. 覆盖分支：同一属性两处定义

### 问题

**实例**：`.advlist .ai`

| 行号 | 声明 |
| --- | --- |
| `app.css:1362` | 基规则（`width:126px`） |
| `app.css:1451` | `@media(max-width:360px){ .advlist .ai{width:112px} }` |

而 `app.css:1449-1450` 的注释**亲口承认了这个坑**：

> `/* 96 → 112px：'#276 09-29 00:00' 实测文本宽 105px（12px 字号），96 装不下会被省略号截断（用户真机正好命中这个 ≤360 分支）。改基规则的宽度没用，这里是另一份。 */`

git 历史为此**误修两次**：

```
fix(web): 冒险页明细行的日期被截断 —— .ai 固定宽度不够
fix(web): 窄屏下日期列仍被截断 —— 漏看了 @media(max-width:360px) 里的那份覆盖
```

**第二例**：`:not()` 特异性族

| 行号 | 选择器 |
| --- | --- |
| `app.css:1621` | `main section[data-page]:not([data-page="main"])` |
| `app.css:1668` | `main section[data-page]:not([data-page="main"]) .subh` |
| `app.css:1673-1676` | 同上 `> .savebtn` / `> .btnrow2` / `> .saveMsg` / `> .plannote` |

特异性 **(0,2,2)**（`:not()` 的参数计入，见 `app.css:1632-1633` 的注释）。一旦 DOM 中间多包一层（`.page-slot` 转场容器就是这么进来的），**整族静默失效** → 内页背景由白变米黄、内容贴边。

### 修复

**C1. 消灭"第二份覆盖"**

`app.css:1451` 的意图是"窄屏下日期列要宽一点"，用**一个表达式**表达两档，而不是两处声明：

```css
/* 合并到基规则一处 */
.advlist .ai{
  /* 窄屏（≤360）需要 112px 才装得下 '#276 09-29 00:00'（实测 105px），
     宽屏用 126px。用 u 表达：360 宽下 112px ≈ 31u，390 宽下 126px ≈ 32.3u —— 
     差异来自"文本宽度固定、u 随视口缩放"，所以必须保留 px 语义。
     用 clamp 表达"下限 112px、上限 126px"： */
  width:clamp(112px, calc(var(--u) * 32), 126px);
}
/* 并删除 @media(max-width:360px) 里的那一份 */
```

> 若 `clamp` 在实机上给的宽度不理想，**退而求其次**：保留两处声明，但在基规则处加醒目注释指向窄屏那份（`/* 窄屏覆盖见 @media(max-width:360px)，改宽度必须两处一起改 */`）。**最差的是现在这样：两处都没有交叉指针。**

**C2. 消灭 `:not()` 特异性族**

改用**显式类**，去掉对 DOM 层级的依赖：

```tsx
// App.tsx 渲染内页时加一个类
<section className={`card page-inner ${name === 'main' ? 'page-home' : ''}`} data-page={name}>
```

```css
/* 用类代替 :not() 链 */
.page-inner{ background:var(--sys-bg) }
.page-inner .subh{ ... }
.page-inner > .savebtn{ ... }
```

这样无论中间包几层容器都不断。

### 影响面与风险

- `.advlist .ai` 的 `clamp` 方案依赖"文本宽固定、u 随视口变"这一事实，**必须真机验证两档宽度**（360 与 390 各测一次）。
- `:not()` 族替换是内页样式的基础，改动面大（1621/1668/1673-1676 + 1632-1633 注释）。建议**独立 PR**，改完逐页截图比对。

### 验收标准

```bash
# 覆盖检测：同一选择器属性出现次数
grep -c '\.advlist \.ai' web/src/styles/app.css                      # 期望 1
grep -c 'section\[data-page\]:not' web/src/styles/app.css            # 期望 0
```

1. 360 宽与 390 宽下，冒险页日期列均完整显示（`'#276 09-29 00:00'` 不截断）。
2. 内页背景色、内容内边距与改动前一致（逐页截图）。
3. 用 04 文档 F 节的 P4 断言（`main` 相关规则命中数 > 0）确认无静默失效。

### 回归风险点

- `FRONTEND_PITFALLS.md` 第 4 节："改结构前 `grep -n 'main >'`，改后逐条确认"。
- 删掉 `:not()` 族后，若有其他地方依赖其 (0,2,2) 特异性来压过别的规则，会失去压制 —— 改完必须全页目视。

## D. 字段清单三份，靠人肉同步

### 问题

同一个"设置字段"集合存在**三份独立副本**：

| 来源 | 数量 | 位置 |
| --- | --- | --- |
| 前端 schema | 55 处 `key:` | `web/src/lib/settings-schema.ts` |
| 通知页硬编码 | **10** 个字段名写死在 JSX | `web/src/components/NotifyPage.tsx:46,54,62,69,77,85,93,100,107,117` |
| 后端映射 | 约 69 字段 | `dashboard.py:1190` 起 `apply_settings` |

且前端类型是 `Record<string, unknown>` —— **拼错字段名不报错，只静默失效**。

### 修复

**D1. 把 NotifyPage 的硬编码挪进 schema**

`NotifyPage.tsx` 里逐条列出的 `notify_feishu_enabled` / `notify_telegram_token` 等 10 个字段，改为从 schema 派生（与设置页同一套渲染机制），消灭第二份清单。

**D2. 加一个能跑的校验测试**（`tests/test_settings_contract.py`）

```python
"""设置字段契约：前端 schema 的 key 必须都在后端 mapping 里，反之只允许白名单例外。

防的是"前端加了字段、后端不认识 → 保存后静默丢配置"这类漂移。
"""
import re
from pathlib import Path

ROOT = Path(__file__).resolve().parent.parent


def _front_schema_keys() -> set[str]:
    src = (ROOT / 'web/src/lib/settings-schema.ts').read_text(encoding='utf-8')
    return set(re.findall(r"key:\s*'([a-z0-9_]+)'", src))


def _back_mapping_keys() -> set[str]:
    src = (ROOT / 'dashboard.py').read_text(encoding='utf-8')
    body = src.split('def apply_settings', 1)[1]
    # 取 mapping 字典里的前端字段名（形如 'xxx_yyy': (...)）
    return set(re.findall(r"'([a-z0-9_]+)':\s*\(", body))


def test_front_keys_are_known_to_backend():
    front, back = _front_schema_keys(), _back_mapping_keys()
    assert front, '没能从前端 schema 解析出任何字段（正则失配？）'
    missing = sorted(front - back)
    assert not missing, f'前端这些字段后端不认识（保存会静默丢失）：{missing}'


def test_backend_has_no_orphan_fields():
    """反向：后端 mapping 有、前端没控件的字段。允许但不静默 —— 列出以便人工确认。"""
    front, back = _front_schema_keys(), _back_mapping_keys()
    orphans = sorted(back - front)
    # 当前存在约 17 个（notify_* 归 NotifyPage、task_order 走 onReorder）
    # 这条不断言为 0，只保证集合稳定、变化时可见
    assert isinstance(orphans, list)
```

### 影响面与风险

- 正则解析 TS 源码是脆弱做法，但**它现在就能跑**，比"等有了代码生成再加"务实。若 schema 结构改动，测试会红 —— 这是期望的信号。
- 当前三方集合无孤儿（已核），所以测试**落地即绿**，成本只是把它钉住。

### 验收标准

```bash
cd /Users/miaopasi/Tools/qq-pet-copilot-mac
python3 -m pytest tests/test_settings_contract.py -v     # 期望 2 passed
```

1. 故意在 `settings-schema.ts` 加一个 `key: 'fake_field'` → 测试必须**变红**。
2. 删掉后恢复绿。
3. `NotifyPage.tsx` 不再出现硬编码字段名（`grep -c "notify_" NotifyPage.tsx` 显著下降）。

### 回归风险点

## E. `?v=` 版本号散落 4 处

### 问题

`/qp-icons/*` 走 `Cache-Control: max-age=3600`，换图后不换 URL 会拿到旧图 1 小时。所以各处在 URL 上挂 `?v=` 做缓存击穿 —— 但版本号散在 4 个地方：

| 位置 | 值 |
| --- | --- |
| `web/src/components/Overview.tsx:96,98` | `?v=2` |
| `web/src/components/FuncBar.tsx:32,42,48` | `?v=5` |
| `web/src/lib/scene.ts:95`（经 `BG_VER`） | `?v=${BG_VER}` |
| `app.css` 里约 10 处静态声明 | `?v=5` |

`Overview.tsx:96` 的注释已承认这个机制：

> `?v=2` 是换图后的缓存击穿（/qp-icons/* 走 max-age=3600，不换 URL 拿旧图 1 小时）

### 修复

**统一为单一入口**：

```ts
// web/src/lib/assets.ts（新增）
/** 图标/背景资源版本号。**换任何 /qp-icons/ 下的图片后必须 +1。**
 *  与 CSS 里的 --qp-* 声明共用一个值（那边是静态的，需手工同步，见下）。 */
export const ICON_VER = '5'
export const icon = (path: string) => `${path}?v=${ICON_VER}`
```

三处 `.tsx` 改为 `icon('/qp-icons/ctrl/play.svg')`。

**CSS 里的 10 处静态声明**无法读 JS 常量，折中方案：用 CSS 变量

```css
:root{ --icon-ver:5 }
.col-l .rbtn img{ background-image:url('/qp-icons/x.svg?v=5') }   /* CSS 的 url() 不能用变量拼 */
```

> 严格说 CSS 的 `url()` **不能**插值变量，所以 CSS 侧只能靠注释约定。**在 `:root` 的 `--icon-ver` 与 `assets.ts` 的 `ICON_VER` 两处都写明"改图时必须同时改这两个 + 所有 CSS url() 的 v"**，并把这个清单写进 `FRONTEND_PITFALLS.md`。

### 影响面与风险

- 版本号统一后，`Overview.tsx` 的 `?v=2` 会变成 `?v=5` —— 一次性多刷一次缓存，无害。
- 真正的风险是"以为统一了就安全"：CSS 侧那 10 处仍是手改，**必须保留 checklist**。

### 验收标准

```bash
grep -rn '?v=' web/src/ --include=*.tsx --include=*.ts | grep -v 'icon(' | grep -v 'assets.ts'   # 期望空
grep -c '?v=5' web/src/styles/app.css   # 已知的 10 处，改图时须全改
```

1. 换一张图标 → 只改 `assets.ts` 的 `ICON_VER` → 真机上确认新图生效。
2. CSS 里的图按 checklist 手工同步。

### 回归风险点

- `BG_VER`（`scene.ts:12`）是**背景图**的版本号，与图标版本号**分开**（背景图数量多、更新频率不同）。不要合并成一个。

## F. 孤儿设计规范文档

## H. 健壮性缺口

### H1. 零 ErrorBoundary

```bash
grep -rn "ErrorBoundary\|componentDidCatch" web/src/ | wc -l   # 实测 0
```

**任何渲染期异常 = 整页白屏**，且没有任何提示或恢复入口。对一个"挂机托管"工具来说，用户不在电脑前时白屏等于失联。

**修复**（`web/src/components/ErrorBoundary.tsx` 新增）：

```tsx
import { Component, type ErrorInfo, type ReactNode } from 'react'

type Props = { children: ReactNode }
type State = { err: Error | null }

export class ErrorBoundary extends Component<Props, State> {
  state: State = { err: null }

  static getDerivedStateFromError(err: Error): State {
    return { err }
  }

  componentDidCatch(err: Error, info: ErrorInfo) {
    // 保留现场：控制台 + 便于用户复制反馈
    console.error('[ui] 渲染异常', err, info.componentStack)
  }

  render() {
    if (!this.state.err) return this.props.children
    return (
      <div style={{ padding: 24, fontFamily: 'system-ui', lineHeight: 1.6 }}>
        <h2 style={{ margin: '0 0 8px' }}>界面出错了</h2>
        <p style={{ color: '#666', margin: '0 0 16px' }}>
          托管进程不受影响，正在继续运行。刷新页面即可恢复。
        </p>
        <pre style={{
          background: '#F2F2F7', padding: 12, borderRadius: 8,
          fontSize: 12, overflow: 'auto', maxHeight: 200,
        }}>{String(this.state.err?.message || this.state.err)}</pre>
        <button
          onClick={() => location.reload()}
          style={{ marginTop: 16, padding: '10px 20px', fontSize: 15, borderRadius: 8 }}
        >重新加载</button>
      </div>
    )
  }
}
```

用法：在 `main.tsx` 里包住 `<App />`。

**关键**：文案要明确告诉用户"**托管进程不受影响**" —— 这是本工具的核心心理需求。

### H2. 乐观更新无回滚

`web/src/components/TaskList.tsx:194-213`：

```tsx
const [optim, setOptim] = useState<Record<string, boolean>>({})
const serverOn = (k: string) => (qt[k]?.state ?? '') !== 'disabled'

useEffect(() => {
  setOptim((prev) => {
    const next: Record<string, boolean> = {}
    let dropped = false
    for (const k of Object.keys(prev)) {
      if (serverOn(k) === prev[k]) dropped = true
      else next[k] = prev[k]!
    }
    return dropped ? next : prev
  })
}, [qt])

const effectiveOn = (k: string) => optim[k] ?? serverOn(k)
const handleToggle = (k: string, on: boolean) => {
  setOptim((p) => ({ ...p, [k]: on }))
  onToggle(k, on)
}
```

清除条件是"服务端状态与本地一致"。**如果保存失败**，服务端状态永远不变 → `optim[k]` **永不消解** → 勾选状态与真实配置长期不符，直到整页刷新。

**修复**：给乐观更新加超时/失败回滚。

```tsx
const handleToggle = async (k: string, on: boolean) => {
  setOptim((p) => ({ ...p, [k]: on }))
  const timer = window.setTimeout(() => {
    // 8 秒内服务端仍未确认 → 视为失败，回滚本地覆盖
    setOptim((p) => { const n = { ...p }; delete n[k]; return n })
  }, 8000)
  try {
    await onToggle(k, on)          // onToggle 需返回 Promise
  } catch {
    window.clearTimeout(timer)
    setOptim((p) => { const n = { ...p }; delete n[k]; return n })
    // 复用 01 文档第 4 节的失败通道
  }
}
```

> 前提：`TaskList` 的 `onToggle` 需要从 `void onToggle(...)` 改为返回 Promise（`App.tsx` 侧对应调整）。

### H3. 直播心跳不看后台

`web/src/lib/usePoll.ts` 有 `document.hidden` 检查（约 62-65 行），但 `web/src/components/LivePage.tsx:217-246` 的 3 秒心跳**没有**：

后果：PWA 切到后台后仍每 3 秒打一次 ping + status 请求，白白耗电（手机端尤其明显），也让服务端的"有人在看"判断失真。

**修复**：

```tsx
// LivePage 心跳内
useEffect(() => {
  const t = window.setInterval(() => {
    if (document.hidden) return        // ← 后台不打
    void livePing()
    void liveStatus()
  }, 3000)
  return () => window.clearInterval(t)
}, [])
```

> 注意：`stop()` 只在 unmount（`LivePage.tsx:250`）触发，PWA 切后台不会 unmount —— 所以仅靠现有逻辑不会自动停，必须显式判 `hidden`。

### 验收标准

1. **ErrorBoundary**：在某个组件里临时 `throw new Error('test')` → 页面显示错误页而非白屏，且含"重新加载"按钮。
2. **乐观更新**：断网后点勾选框 → 8 秒内勾选状态回滚到真实值。
3. **心跳**：真机切到后台 1 分钟 → 服务端日志无新增 ping（`grep live-ping runs/logs/dashboard.log`）。

### 回归风险点

- ErrorBoundary 只能捕获**渲染期**异常，不能捕获事件处理器/异步里的 —— 那些仍需各处 try/catch（见 01 文档第 2 节）。
- 乐观更新加回滚后，快速连点可能触发"回滚晚于新操作"，需要按 key 独立计时。
