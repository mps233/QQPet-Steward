## A. 高度链上锁（把"祖先链确定高度"收敛成显式规则块）

### A.1 问题

`.home` 这一层的全部子元素都是 `.flt{position:absolute}`（`app.css:243`），绝对定位元素**不产生父级高度**；而 `.home` 靠 `min-height:100%`（`app.css:237-238`）拿高度，百分比在 `min-height` 里必须相对**已确定高度的父级**解析。整条链上任何一层变成"由内容撑高"，百分比就失效 → 整页塌成只剩背景。

`FRONTEND_PITFALLS.md:22` 记录这个错**犯过 3 次**，断点依次在 `.app`、`main`、`.page-slot`；`app.css:170-173` 的注释也自陈"实测两次踩坑"。

当前链条的 8 条规则分散在文件三处、跨 1428 行：

| 层 | 规则 | 行号 |
| --- | --- | --- |
| `html` | `height:100%;min-height:100%` | 120-121 |
| `body` | `height:100%`（同时是唯一滚动容器）+ `overscroll-behavior:none` | 156-159 |
| `#root` | `display:contents`（布局上消失） | 1548 |
| `.app` | `height:100%` | 174 |
| `.app > main` | `height:100%` + `position:relative` | 175 / 184 |
| `.page-slot` | `position:absolute;inset:0;overflow-y:auto` | 195-198 |
| `.home` | `min-height:calc(100vh - safe-top)` 兜底 + `min-height:100%` | 237-238 |
| 内页 `section[data-page]` | `min-height:100%` | 1627 |

外加两条**隐性契约**：`.home{position:relative}`（`app.css:220`，给内部 `.flt` 当包含块）和 `#root{display:contents}`（`app.css:1548`，让 `.app` 直接成为 `body` 的布局子元素，避开 iOS 根滚动器判定，见 1539-1547 注释）。

**为什么 `position:relative` 是禁招（要理解到机制，不能只背口诀）**：

`PITFALLS:28-29` 说"给 `.home` 或其祖先加 `position:relative` 也会踩"，但**并不是 relative 本身有害**——`.home` 自己就是 relative（220 行）且必须如此。真正发生的是：

`.page-slot` 现在是 `position:absolute; inset:0`（195-196），它的高度**由 inset 锁定为一屏**，与内容无关。一旦把它改成 `position:relative`，它会退化回**正常流元素 → 高度由内容决定 → 内容里全是绝对定位 → 高度塌成 0**；然后 `.home{min-height:100%}` 相对这个 0 高父级解析，百分比失效，整页只剩 `html` 的背景图。

**判定规则（写进 review checklist）**：高度链上的层要么 `height:100%`（父级高度已确定），要么 `position:absolute; inset:0`。**只有 `inset` 那一层不允许改成 `relative`**；`.home` 这种"自身就是内容容器、只需要定位锚点"的层，`relative` 是必需的。

### A.2 修复：建"骨架契约"区块

在 `app.css` 第 3 节（现 168 行 `/* ---------- 3. 骨架：480dp 浮动层舞台 ---------- */` 处）集中写一份**唯一真源**，其余位置留指针注释。**值一律不变，纯搬迁**——这是它能被安全评审的前提。

```css
/* ============================================================
   S0 · 舞台高度锁（唯一真源 · 改动前先读 docs/review/04-布局系统与高度链.md）
   ------------------------------------------------------------
   契约：从 html 到 section[data-page] 的每一层必须"高度已确定"。
   .home / 内页容器里全是 position:absolute 的浮动层，撑不开父级；
   min-height:100% 依赖父级有确定高度。断任意一层 → 整页塌成只剩背景。
   历史：这个错犯过 3 次，断点分别在 .app、main、.page-slot。
   规则：① 链条上的层用 height:100% 或 position:absolute;inset:0；
        ② inset 那一层（.page-slot）**绝不能**改成 position:relative；
        ③ 新增任何 wrapper 必须自带 height:100% 或 display:contents；
        ④ 不要在 main 上加 overflow（会二阶裁切，且让 slot 滚动高度算错）。
   ============================================================ */
#root{display:contents}                 /* 布局上消失：.app 直接成为 body 的布局子元素 */
.app,
.app > main{height:100%}
.app > main{position:relative;overflow:visible}
main .page-slot{
  position:absolute;inset:0;            /* ← inset 锁高度，禁用 relative 替代 */
  overflow-y:auto;overflow-x:hidden;
  overscroll-behavior:none;will-change:transform;
}
main section[data-page]{min-height:100%} /* .home 与内页共用 */
```

搬迁映射（原地删除/留注释）：

| 原行号 | 原内容 | 处理 |
| --- | --- | --- |
| 174-175 | `.app,.app > main{height:100%}` | 迁入 S0 |
| 184 | `.app > main{position:relative}` | 与上一条合并，补 `overflow:visible` |
| 195-198 | `.page-slot{...}` | 迁入 S0，选择器改 `main .page-slot`（后代，避开直系陷阱） |
| 237-238 | `.home` 的两条 `min-height` | 保留其一（`100vh - safe-top` 兜底），`min-height:100%` 由 S0 的 `section[data-page]` 接管 |
| 1548 | `#root{display:contents}` | 迁入 S0，原处留指针注释 |
| 1627 | 内页 `min-height:100%` | 由 S0 接管，原处只留背景/内边距 |

**注意 `main section[data-page]{min-height:100%}` 与 1621 行那条 `main section[data-page]:not([data-page="main"])` 的特异性关系**：前者 (0,1,2)，后者 (0,2,2)，后者会压住前者——两条都写 `min-height:100%` 时结果相同，安全。但**不要让 S0 依赖覆盖顺序**，所以 S0 里这条只作兜底，1627 保持不变亦可（二选一，别两处都改）。

## B. 单位基准统一（三处矛盾 → 单一真源）

### B.1 问题

同一文件里三个互斥的说法：

| 行号 | 原文 | 真伪 |
| --- | --- | --- |
| `app.css:114-115` | `/* 1dp = 可用宽度/360 */` + `--u:var(--vu, calc(100vw / 360));` | ✅ **真**（且与 `stage.ts` 一致） |
| `app.css:168-169` | `/* ---------- 3. 骨架：480dp 浮动层舞台 ---------- */` + `单位系统：--u = 1dp = 屏宽/480。官方逻辑画布就是 480dp` | ❌ **假**（基准早就是 360） |
| `app.css:224` | `官方画布 853dp；用 --u 乘出来即可` | ⚠️ **易误导**（853 是纵向参考高，不是宽度基准） |

权威实现是 `web/src/lib/stage.ts`：

```ts
// stage.ts:9-16
const setU = () => {
  const w = document.documentElement.clientWidth || window.innerWidth
  document.documentElement.style.setProperty('--vu', `${w / 360}px`)
}
```

它写 `--vu`，CSS 侧 `--u:var(--vu, calc(100vw / 360))` 只在 JS 未执行时兜底。`--vu` 全项目**只有 115 行一个消费点**（`rg -n -- '\-\-vu' web/src` 仅 2 处命中：stage.ts 定义 + app.css 消费），所以基准的单一真源是清晰的，脏的只是注释。

### B.2 统一结论（本节必须钉死的四件事）

1. **基准 = 360**。官方手机版逻辑画布宽 360dp（真机 density 480）。`app.css:214-217` 自己算过账：按钮 42dp 在 360dp 画布上占屏宽 11.67%；若按 480dp 画布做只占 8.75%，"明显偏小（实测小了 25%）"。**480 是平板/模拟器版画布，用它就是错的**。
2. **853 不是画布宽度，是纵向参考高度**。853 ≈ 1080×2412 的物理分辨率换算到 360dp 宽画布后的高度量级（2412 / 2.828 ≈ 853）。**纵向坐标全部是绝对值 `N × u`，不参与任何推导，所以这句话可以整句删掉**，改成对 360 的一句话说明。
3. **正确注释**（直接替换 168-169 两行）：

```css
/* ---------- 3. 骨架：360dp 浮动层舞台 ---------- */
/* 单位系统：--u = 1dp = 可用宽度 / 360（手机版逻辑画布宽 360dp，真机 density 480）。
   由 lib/stage.ts 写 --vu（用 clientWidth 而不是 100vw —— 后者含滚动条宽，会让坐标偏大约 2%），
   本文件第 115 行的 `calc(100vw / 360)` 只是 JS 未执行时的兜底。
   480dp 是平板/模拟器版画布，坐标不要按它换算（会让元素小 25%）。
   纵向坐标一律写绝对值 `N × u`，不依赖任何"画布高度"概念。 */
```

4. 同步修正 `app.css:224`（删掉"官方画布 853dp"，保留后半句的 `calc(100% * N)` 警告——那条警告是对的）。

### B.3 影响面与风险

渲染结果**完全不变**（只动注释）。真正的收益是**消除认知陷阱**：下一个改 UI 的人（或 AI）照 169 行按 480 算，会写出系统性偏小 25% 的坐标，且因为"看起来有注释背书"而不会怀疑——这是本项目反复返工的一个机制性原因。

### B.4 验收

```bash
rg -n '480dp|屏宽/480' web/src/styles/app.css                    # 期望：0 命中
rg -n -- '--u:' web/src/styles/app.css                            # 期望：仅 115 行 1 处
rg -n -- '--vu' web/src/lib/stage.ts web/src/styles/app.css       # 期望：定义 1 + 消费 1
```

### B.5 回归风险点

- 后续加断点时若临时覆写 `--u`（如 E 节的 clamp），**必须同步更新 115 行的注释**，否则又会出现第二处基准声明。约定：`--u` 的定义点全项目唯一，任何覆写都必须紧邻它写。

## C. 299 处手算坐标：先分类，再分批

### C.1 问题（附实测分布）

`rg -o 'calc\(var\(--u\)' app.css | wc -l` = **299**。逐条按属性归类（awk 拆声明统计）：

| 属性 | 出现次数 | 归类 | 是否该 token 化 |
| --- | --- | --- | --- |
| `font-size` | 49 | 字号 | ✅ 该 |
| `padding` / `padding-*` | 32 + 6 | 间距 | ✅ 该 |
| `gap` | 24 | 间距 | ✅ 该 |
| `border-radius` | 19 | 圆角 | ✅ 该（且已有 `--r-*` 阶梯可复用） |
| `margin*` | 8+3+2+1+1 | 间距 | ✅ 该 |
| `min-height` / `max-height` | 3 + 1 | 尺寸 | ⚠️ 混合 |
| `height` | 23 | 尺寸 | ❌ 多为控件实测高度（如 `.mcb` 19u） |
| `width` | 17 | 尺寸 | ❌ 同上 |
| `top`/`left`/`bottom`/`right` | 13+6+3+1 | 坐标 | ❌ **官方实测坐标，绝不能 token 化** |
| 选择器行误计 | ≈ 12 | — | — |

**结论：299 处里只有约 140 处（字号 + 间距 + 圆角，≈47%）该动**。坐标与控件尺寸（约 59 处）是"复刻官方截图"的产物——把它们抽成 `--sp-3` 之类的名字会**毁掉"这一行对应官方哪个实测值"的可追溯性**，让下一个对着 `UI_TREE_OFFICIAL.md` 校准的人无从下手。这是本节最重要的判断：**不是所有魔法数字都是技术债**。

已 token 化的部分比预想的多（**不要从零建体系**）：

- 圆角阶梯 4 档：`app.css:90` `--r-sm:6px; --r-md:10px; --r-lg:14px; --r-xl:18px;`（注释标注来源 TDesign）
- 阴影 2 档：`app.css:93-94` `--sh-1` / `--sh-2`
- 顶部纵向布局 6 个 token + 推导链：`app.css:28-36`（`--top-card`/`--h-card`/`--h-cap`/`--gap-top` → `--top-caps`/`--top-scene`），注释 32 行明写"不要再手写数字，否则改了间距就对不上"
- 间距单点：`app.css:31` `--gap-top:12`，并在三个断点被改写为 10/8/6（1446 / 1468 / 1476）

**缺的是两样**：通用 spacing 阶梯、字号阶梯。而且已有 token 的**单位约定是"无单位数值 × u"**（`app.css:35-36`、`442` 用了 `calc(var(--u) * (var(--h-card) - 6))`）——新阶梯必须沿用这个约定，不能改成 px，否则两套单位制混用会比现在更糟。

### C.2 修复：阶梯按实测频率定，不拍脑袋

对取值做频率统计（`rg -o 'calc\(var\(--u\) ?\* ?[0-9.]+'`），得到实际使用 Top 值：

| 值 (u) | 次数 | 值 (u) | 次数 |
| --- | --- | --- | --- |
| 12 | 23 | 9 | 10 |
| 10 | 21 | 20 | 9 |
| 2 | 19 | 3 | 8 |
| 6 | 17 | 13 | 7 |
| 8 | 16 | 11.5 | 7 |
| 14 | 16 | 7 | 6 |
| 16 | 14 | 18 / 12.5 / 10.5 | 各 5 |
| 4 | 11 | 17 | 4 |

据此定义（**沿用无单位数值约定**）：

```css
/* 间距阶梯（单位：u，与 --gap-top 同制；命名对齐 TDesign 的 4 档基数） */
--sp-1:2;   --sp-2:4;   --sp-3:6;   --sp-4:8;   --sp-5:10;
--sp-6:12;  --sp-7:14;  --sp-8:16;  --sp-9:20;  --sp-10:24;
/* 字号阶梯（本项目的字号密集在 10.5~14 之间，共 6 档） */
--fs-1:10.5; --fs-2:11.5; --fs-3:12; --fs-4:12.5; --fs-5:13; --fs-6:14;
```

依据：`--sp-6:12` 与 `--sp-5:10` 是出现最多的两个值（23 / 21 次），阶梯必须覆盖它们，否则迁移时会忍不住写回字面量；`--fs-*` 六档直接覆盖 Top 里的 10.5 / 11.5 / 12 / 12.5 / 13 / 14。

### C.3 分批迁移（**不要一次改完 299 处**）

**批次 0（先决条件，1 小时）**：只加 token 定义 + 一条规则，**不改任何使用点**。

> 规则：新增或修改的 CSS，间距类属性必须用 `--sp-*`，字号必须用 `--fs-*`；坐标类（`left/top/width/height`）保持 `N × u` 字面量并保留"官方实测"注释。

这条写进 `web/FRONTEND_PITFALLS.md` 与 PR 模板，比一次性重写 299 处更有效。

**批次 1（机械替换，半天）**：只替换**取值恰好命中阶梯**的使用点，`sed` 可完成、diff 可逐条审。

```bash
# 示例：把 font-size:calc(var(--u) * 12) 换成 font-size:calc(var(--u) * var(--fs-3))
sed -i '' 's/font-size:calc(var(--u) \* 12)/font-size:calc(var(--u) * var(--fs-3))/g' web/src/styles/app.css
```

预计覆盖约 60% 的字号与间距使用点。**先做字号（49 处，收益最高、视觉零风险）**。

**批次 2（人工判断，1 天）**：取值不在阶梯上的使用点，逐个决定"改到最近档"还是"保留字面量"。判定标准：**改完是否与某个官方实测值脱钩**。脱钩的保留。

**批次 3（断点收口，半天）**：把断点里的覆盖值改成改 token 而不是改属性（项目已有先例：`app.css:1446`/`1468`/`1476` 都是 `:root{--gap-top:N}`）。批次 1-2 完成后，`--gap-top` 可以并入 `--sp-*` 体系。

**不做**：坐标迁移。

### C.4 影响面与风险

- 批次 1 是纯文本替换，但**必须逐行审 diff**：`calc(var(--u) * 12)` 也可能是官方实测坐标的偶然值（例如某个 `width`），用 `sed` 时要带属性前缀限定（如上例的 `font-size:`）。
- 改字号会让文本换行位置变化 → 可能触发被省略号截断的文本（本项目有历史事故：`#276 09-29 00:00` 实测宽 105px 装不下，见 `app.css:1449-1451`）。批次 1 只替换**等值**，不产生视觉变化，所以安全；批次 2 若改到最近档（±0.5u）需真机看一次。

### C.5 验收

```bash
rg -n -- '--sp-6:12|--fs-3:12' web/src/styles/app.css                                   # 阶梯已定义
rg -c 'font-size:calc\(var\(--u\) \* var\(--fs-' web/src/styles/app.css                  # 迁移进度（目标 >60%）
rg -n '(left|top|width|height):calc\(var\(--u\) \* var\(--sp-' web/src/styles/app.css    # 坐标未被误迁移（期望 0）
```

### C.6 回归风险点

- 阶梯与字面量**长期并存**是预期状态，不是失败。若为了"干净"强行统一到阶梯，会把官方校准值抹平，下次对着截图微调时无从下手。
- 批次 3 收口断点值时，注意 `--gap-top` 在 `:root` 与断点里同步改写的模式（1446/1468/1476 三处），漏一处就会出现"某个宽度下间距不对"——这是窄屏补丁史的同一类错误。

## D. 圆钮栅格与"取平均"的临时解

### D.1 问题

`app.css:722-728` 的注释自陈：

```
top = 右列第三颗圆钮的底 + **两倍半圆钮间距**
算一下：第三钮 top 154.3u + 高 42u = 196.3u；圆钮之间的空隙
16u（第 1→2）/ 18u（第 2→3），取 17u → 2.5 倍 42.5u → 196.3 + 42.5 ≈ 238.8u。
（调这个值时只改这一个数即可：几倍间距 = (top − 196.3) / 17。）
```

而实际坐标（`app.css:249-256`）：

| 位置 | 左列 y | 右列 y |
| --- | --- | --- |
| 第 1 颗 | 36.3 | 36.3 |
| 第 2 颗 | 94.3 | 94.3 |
| 第 3 颗 | 154.3 | 154.3 |
| 第 4 颗 | 214.3 | — |

步长 58 / 60 / 60，圆钮高 42u（`app.css:259`）→ 空隙 16 / 18 / 18。**官方原值本身就不等距**，这不是抄错。

代价是 `.funcbar` 的 `top`（238.8u）建立在一个"平均数 17u"上，注释里还留了一条逆运算公式。任何一颗圆钮改 y 或改尺寸，`.funcbar` 必须重算——而它俩在文件里相隔 470 行（249 vs 728），没有任何机制提醒。"功能栏压住第三颗圆钮"在历史上就发生过（`app.css:726-727` 记录原值 190u < 196.3u）。

### D.2 修复：抽 token，**不改数值**

```css
/* :root 内，与 --h-card 等同区 */
--btn-sz:42;          /* 圆钮直径 */
--btn-x-l:20;         /* 左列 x */
--btn-x-r:298;        /* 右列 x */
--btn-y0:36.3;        /* 第 1 颗 y（官方实测） */
--btn-y2:154.3;       /* 第 3 颗 y（官方实测，保留真值不参与推导） */
--btn-last-bottom:calc(var(--btn-y2) + var(--btn-sz));   /* 196.3 */
--btn-gap-avg:17;     /* 官方 16/18 的平均；只用于 .funcbar 这类"需要一个数"的推导 */
```

坐标行保持字面量（可追溯官方值），只把**推导关系** token 化：

```css
/* before（249-256）：坐标各自为政，.funcbar 不知它们存在 */
.col-l .rbtn:nth-child(3){left:calc(var(--u)*20);top:calc(var(--u)*154.3)}

/* after：坐标值不变，只是引用 token */
.col-l .rbtn:nth-child(3){left:calc(var(--u)*var(--btn-x-l));top:calc(var(--u)*var(--btn-y2))}
```

`.funcbar` 的 `top` 改为可推导形式（**保留 238.8 这个结果值**，避免视觉变化）：

```css
/* before（728） */
top:calc(var(--u) * 238.8);
/* after */
top:calc(var(--u) * (var(--btn-last-bottom) + 2.5 * var(--btn-gap-avg)));
```

**是否要把三颗圆钮改成等距（统一 18u）？不建议。** 那会偏离官方实测坐标，让 `UI_TREE_OFFICIAL.md` 的逐项对齐失效——收益是"注释更干净"，代价是"复刻准确度下降"。停在这一步。

### D.3 影响面与风险

- 纯 token 抽取，计算路径等价（`196.3 + 42.5 = 238.8` 逐位复现）。唯一风险是 `calc` 嵌套写法——变量内是**无单位数值**，所以内层 `calc` 可省略（项目已有先例：`app.css:35-36`、`442`）。

### D.4 验收

探针内读 computed style：`getComputedStyle(document.querySelector('.funcbar')).top`，期望 = `238.8 × (clientWidth/360) px`。手工核对：三颗圆钮的 `getBoundingClientRect()` 在改动前后**逐像素一致**。

### D.5 回归风险点

- 若将来真的按"等距 60u"重排圆钮（例如用户要求更整齐），必须同时改 `--btn-y2` 与步长，`--btn-last-bottom` 会自动跟随——这正是把它 token 化的意义。改完必须真机截图比对，`UI_TREE_OFFICIAL.md` 也要同步。

## E. 断点策略：`--u` 上下限、版心、平板与横屏

### E.1 问题

实测 8 个媒体查询（awk 按花括号深度统计规则数）：

| 断点 | 行号 | 规则数 | 用途 |
| --- | --- | --- | --- |
| `prefers-reduced-motion` | 209-211 | 1 | 关页面转场动画 |
| `max-width:639px` | 1430-1436 | 1 | 只剩 `.ttag{display:none}`（历史补丁已清理，见 1431-1434 注释） |
| **`max-width:360px`** | 1438-1454 | 11 | 小屏收紧 + `.advlist .ai` 二次覆盖 |
| `min-aspect-ratio:360/700` | 1467-1472 | 4 | 短屏收紧纵向间距 |
| `min-aspect-ratio:360/620` | 1475-1486 | 3 | 更短屏 + **隐藏"画面"按钮**（1485） |
| `min-width:640px` | 1487-1490 | 2 | 只改 grid 列数 |
| `min-width:920px` | 1492-1496 | 3 | 只改 grid 列数 + `#logbox` 高度 |
| `prefers-color-scheme:dark` | 1502-1518 | 1 | 只换背景图 token |

短屏判据用 `min-aspect-ratio` 而不是屏高，理由在 `app.css:1456-1465` 写得很清楚（所有纵向尺寸都是 `N × u`，`u = 屏宽/360`，所以"够不够高"本质是比例问题）——**这个设计是对的，保留**。

真正的问题是三个：

**① `--u` 无上限**——`app.css:115` 是裸的 `calc(100vw / 360)`（`stage.ts` 同样不设限）。iPad 竖屏 768 宽：

| 元素 | 定义 | iPad 768 | 手机 390 |
| --- | --- | --- | --- |
| `--u` | 视口宽/360 | **2.133px** | 1.083px |
| 圆钮 `.rbtn` | 42u（259） | **89.6px** | 45.5px |
| 任务卡标签字号 | 10.5u（608） | **22.4px** | 11.4px |
| 任务名 | 12.5u（984） | **26.7px** | 13.5px |

即：**版式按 360dp 设计，在平板上被等比放大 2.13 倍**，一屏只放得下三行任务。

**② 没有版心**——`min-width:640px` / `min-width:920px`（1487-1496）只改 grid 列数，**没有任何 `max-width`**。桌面上整页横向拉满，浮动层（`.idcard{left:74u;width:207u}`、`.scene{left:74u;width:207u}`，412-420 / 693-694）靠左堆在一条 207u 宽的竖条里。

**③ 横屏完全没处理**——844×390（iPhone 横屏）：`--u = 2.344`，且宽高比 2.16 ≥ 0.5143（`360/700`）与 0.5806（`360/620`）**两档同时命中**，也就是"巨物 + 砍两轮纵向间距 + 隐藏画面按钮"三件事一起发生。竖向内容需要 853u × 2.344 = **2000px**，视口只有 390px。

### E.2 修复

**E.2.1 `--u` 加 clamp（一处改动）**

`--vu` 全项目只有 115 行一个消费点，所以**只改 CSS 一处**即可，`stage.ts` 不动：

```css
/* before（115） */
--u:var(--vu, calc(100vw / 360));
/* after */
--u-min:0.9px;    /* ≈ 324px 视口；再窄就靠横向内边距吃，不再缩元素 */
--u-max:1.2px;    /* = 432px 视口（iPhone Pro Max 430 正好落在上限内） */
--u:clamp(var(--u-min), var(--vu, calc(100vw / 360)), var(--u-max));
```

为什么写在 CSS 而不是 `stage.ts`：`stage.ts` 的职责是"量 clientWidth 去掉滚动条误差"（`app.css:218` 的解释），它是**原始测量**；上下限是**设计决策**，属于设计系统层。放 CSS 里还能顺带覆盖 JS 未执行的首帧。两处若都写，日后必然不同步。

⚠️ `clamp()` 三个参数都必须是长度：`var(--vu)` 是 `2.133px` 形式 ✓，兜底 `calc(100vw / 360)` 也是长度 ✓。

**E.2.2 版心**

```css
/* 大屏不再横向拉满：舞台限宽居中，html 的背景图仍然铺满 */
@media (min-width:640px){
  .app{max-width:430px;margin:0 auto;
       box-shadow:0 0 0 1px rgba(0,0,0,.06), 0 8px 40px rgba(0,0,0,.18);}
  .home{max-width:100%;}      /* 覆盖 221 行的 max-width:100vw，否则版心内仍按视口宽算 */
}
```

**连带影响（必须一起处理）**：以下元素是 `position:fixed`，包含块是视口而不是 `.app`，版心限宽后它们会横跨整屏：

| 元素 | 行号 | 处理 |
| --- | --- | --- |
| `#bgSheet` | 360（`position:fixed;inset:0`） | 加 `left:50%;transform:translateX(-50%);width:min(100vw,430px)` |
| `#torderToast` | 965（`position:fixed;left:50%`） | 已有 `left:50%` 居中，仅需 `max-width:430px` |
| `.shotpage .livetoast` | 1077 | 是 `absolute`，不受影响 |

**E.2.3 横屏：给"最小可用版"，并明确它在哪一步止步**

先说清楚为什么没有优雅解：本项目的布局模型是"把官方 360dp × 853u 的竖屏画布用绝对坐标复刻"。横屏 844×390 时，**沿宽度算 u = 2.34（元素巨大且纵向放不下），沿高度算 u = 0.457（按钮只有 19px 不可点）**——在绝对定位模型下两个方向都无解。真正的横屏体验需要把 `.home` 从"绝对定位舞台"改成 grid/flex 布局，那是 A 节之外的模型重写，量级 ≥ 3 人天，**本次不做**。

本次给最小可用版：横屏时改成"高度基准 + 任务面板右移"的伪两栏。

```css
/* 横屏（矮屏）：基准换成视口高，元素尺寸与竖屏一致；任务面板挪到右侧空白区 */
@media (orientation:landscape) and (max-height:520px){
  :root{
    /* 横屏的稀缺资源是高度：1u 按高度算（390 高 → 1.083px，与 390 宽竖屏一致） */
    --u:clamp(var(--u-min), calc(100vh / 360), var(--u-max));
  }
  .app{max-width:none}

  /* 左栏（原地）：资料卡 + 胶囊 + 圆钮，保持官方坐标 */
  /* 右栏：任务面板从 380u 起（右侧空区），占满可用高度 */
  .scene{
    left:calc(var(--u) * 380);
    width:calc(100% - calc(var(--u) * 390));
    top:calc(var(--u) * 10);
    max-height:calc(100% - calc(var(--u) * 20));
  }
  .deck{width:calc(var(--u) * 360)}          /* 底栏只覆盖左舞台 */
  .col-r .rbtn{left:calc(var(--u) * 340)}    /* 右列圆钮收进左舞台右缘 */
  .funcbar{left:calc(var(--u) * 340)}
}
```

坐标值需真机/探针校准一次（`.scene` 的 380u 起点要避开右列圆钮的 340~382u 区间）。量法：

```js
// 探针内
const r = el => { const b = el.getBoundingClientRect(); return [b.left, b.top, b.right, b.bottom].map(Math.round) }
// 期望：r('.col-r .rbtn:last-child')[2] < r('.scene')[0]
```

### E.3 影响面与风险

- **clamp 上限 1.2 会影响所有 > 432px 视口**：桌面 1440 宽下 `--u` 从 4.0px 变成 1.2px，元素缩小 3.3 倍。这是**期望行为**（当前桌面下整页是巨物），但会改变现有桌面观感，需一次人工确认。若只想先修平板，可临时把上限设为 `768/360 = 2.13px`，分两步走。
- 版心加在 `.app` 上：`.app{height:100%}` 不变，高度链不受影响（A 节契约仍成立）。但要确认 `.home{max-width:100vw}`（221）同步改 `100%`，否则 `.home` 仍按视口宽算 → 溢出。
- 横屏伪两栏是**新增行为**，风险最高，建议独立 PR + 真机截图。

### E.4 验收

各视口 `--u` 期望值：`320×568 → 0.9px`（触下限）/ `360×640 → 1.0px` / `390×844 → 1.083px` / `430×932 → 1.194px` / `768×1024 → 1.2px`（触上限）/ `844×390` 横屏 `→ 1.083px`。

平板验收的直观判据：**768 宽下 `.rbtn` 宽度应 ≤ 51px，任务卡字号 ≤ 15px**（当前分别是 89.6px / 22.4px）。

### E.5 回归风险点

- `clamp` 下限 0.9px 会让 ≤324px 视口的元素略大于比例值。320 宽正好在边缘：320/360 = 0.889 < 0.9 → 元素比比例值大 1.2%，`.idcard{width:207u}` = 186.3px vs 比例值 184px，差 2.3px，仍能放下 ✓。
- 横屏断点用 `(orientation:landscape) and (max-height:520px)`：iPad 横屏（1024×768）`max-height:768 > 520` 不命中，会走"版心 + clamp"，那是正确的。

### F.2 `tools/assert-layout.py`（全文）

```python
#!/usr/bin/env python3
"""布局体检断言。用法：python3 tools/assert-layout.py report.jsonl（每行一个探针 JSON）。"""
import json, sys

def main(path):
    rows, fail = [], 0
    with open(path, encoding="utf-8") as fh:
        for line in fh:
            line = line.strip()
            if not line:
                continue
            r = json.loads(line)
            tag, notes = "PASS", []

            if r.get("probeMissing"):
                tag, notes = "FAIL", ["探针无输出（页面没渲染完？）"]
            else:
                vw, vh = r["vp"]
                # P1 舞台高度：.home 高度 ≈ 视口高（±1.5px）
                if r["homeH"] is None:
                    tag, notes = "FAIL", ["找不到 .home"]
                elif abs(r["homeH"] - vh) > 1.5:
                    tag = "FAIL"
                    notes.append(".home 高 %.2f ≠ 视口高 %d（差 %.2f）" % (r["homeH"], vh, r["homeH"] - vh))
                # P2 总览页 .home 不该滚（内页的滚动发生在 .page-slot，是正常的）
                if r["page"] == "main" and r["homeOverflow"] not in (None, 0):
                    tag = "FAIL"; notes.append("总览页 .home 溢出 %dpx" % r["homeOverflow"])
                # P3 结构契约：main 的直系子应是 .page-slot（转场容器）
                kids = r["mainKids"]
                if not kids or not all(k.startswith("div.page-slot") for k in kids):
                    tag = "FAIL"; notes.append("main 直系子异常：%s" % kids)
                # P4 选择器失效体检：命中数为 0 的 main 相关规则 = 静默回归
                dead = [s for s, n in r["rules"] if n == 0]
                if dead:
                    tag = "FAIL"; notes.append("失效规则：" + " | ".join(dead[:3]))
                # P5 单位基准上限（提示级）
                u = r["uVar"]
                if u.endswith("px"):
                    try:
                        uf = float(u[:-2])
                        if uf > 1.35:
                            notes.append("--u=%.3fpx 超过 1.2 上限（E 节未修？）" % uf)
                    except ValueError:
                        pass
                if r.get("ready") is False:
                    notes.append("数据未加载完（断言仍有效：骨架高度与数据无关）")
            rows.append((r.get("size", "?"), r.get("page", "?"), tag,
                         r.get("homeH"), r.get("vp", [0, 0])[1], r.get("uVar", ""),
                         r.get("btnW"), r.get("fsTask"), "；".join(notes)))
            if tag == "FAIL":
                fail = 1

    if not rows:
        print("❌ 没有任何探针结果"); return 2
    w = max(len(x[0]) for x in rows)
    print("%s  页   结果  .home高  视口高  --u        圆钮宽  任务字号  说明" % "尺寸".ljust(w))
    for s, p, t, h, vh, u, bw, fs, note in rows:
        print("%s  %-4s %-4s %7s %7s %8s %7s %8s  %s"
              % (s.ljust(w), p, t, h, vh, u, bw, fs, note))
    print()
    print("✅ 全部通过" if not fail else "❌ 存在失败项")
    return fail

if __name__ == "__main__":
    sys.exit(main(sys.argv[1] if len(sys.argv) > 1 else "report.jsonl"))
```

### F.3 断言表与落地清单

| 编号 | 断言 | 失败含义 |
| --- | --- | --- |
| P1 | `abs(.home 高 − 视口高) ≤ 1.5px` | 高度链断裂（A 节的错又犯了） |
| P2 | 总览页 `.home` 的 `scrollHeight − clientHeight == 0` | 整页多出一条可滚区 |
| P3 | `main` 直系子全为 `div.page-slot` | 有人往骨架里插了新 wrapper（A 节禁招） |
| P4 | 扫描到的 `main` 相关规则命中数 > 0 | **直系选择器被"多包一层"打断**（静默失效） |
| P5 | `--u ≤ 1.35px` | 提示级：E 节 clamp 未生效 |
| — | `.rbtn` 宽 / `.mname` 字号 | 参考值：平板巨物的量化证据 |

P4 是本脚本最有价值的一条：把"改结构 → 直系选择器整条失效 → 样式静默回退"这个**犯过、且没有任何报错**的错误变成可自动检测的断言。

落地四要求：① 前置 `curl` 健康检查保留；② 断言脚本独立成文件，**不要用 heredoc 抢 stdin**；③ 断言只用与数据加载无关的量；④ 探针必须写在 `web/dist/assets/` 下（放 `/` 下会 404）。

接入：`package.json` 加 `"check:layout": "bash ../tools/layout-check.sh"`；`web/build.sh` 末尾追加 `bash ../tools/layout-check.sh --sizes 390x844`（容忍退出码 2）；`FRONTEND_PITFALLS.md:164-171` 的检查清单加一行本脚本。

### F.4 回归风险点

- headless 里 `env(safe-area-inset-*)` 恒为 0，"屏幕最底下露出约一个 safe-bottom 的背景"这类问题**脚本测不出来**，仍需真机。脚本定位是"防结构回归"，不是"替代真机验收"。
- 768 与 844×390 两个尺寸**在修 E 之前预期失败**。落地时先只跑手机三档（320/360/390），E 节合并后再放开全部。
