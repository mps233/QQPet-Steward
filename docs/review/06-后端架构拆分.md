## A. import 环

### 问题

```
src/scenario.py:641        from scenarios.care import CareScenario
scenarios/care.py:30       from src.scenario import CLICK_INTERVAL, DeviceScenario
```

第一条在 `care_once()` 方法内（函数级延迟导入），第二条在模块顶层。**构成环。**

后果：`import src.scenario` 会连锁拉起整个 `scenarios` 包。这意味着：

- `src/` 包**无法独立加载**，无法单测（任何 `import src.scenario` 的测试都会拖进 10 个场景模块及其依赖）
- 依赖方向本来是单向的（`scenarios` → `src`），这条反向边是**唯一破口**

**为什么会有这条边**：`care_once()` 是"主页面执行一次护理检查"的通用能力，被 PK 场景（`StatBlocked` 后重试）等地方需要。它把"护理业务"塞进了通用基类。

### 修复

改为**注入回调**：基类不 import 具体场景，由调度器在构造时注入。

```python
# src/scenario.py —— DeviceScenario.__init__ 增加可选参数
class DeviceScenario:
    def __init__(self, dev, cfg=None, *, care_fn=None):
        ...
        self._care_fn = care_fn          # 注入的护理回调

    def care_once(self) -> None:
        """主页面执行一次护理检查。具体实现由调用方注入（见 Runner 的构造），
        避免 src 反向依赖 scenarios 形成 import 环。"""
        if self._care_fn is None:
            log('care_once: 未注入护理回调，跳过')
            return
        self._care_fn()
```

```python
# scenarios/runner.py —— 构造场景时注入
from scenarios.care import CareScenario

def _make_care_fn(dev, cfg):
    return lambda: CareScenario(dev, cfg).check_and_care()

scen = SchoolScenario(dev, cfg, care_fn=_make_care_fn(dev, cfg))
```

调用方需要改的地方：所有 `DeviceScenario` 子类的实例化点（`runner.py` 的 `__init__` 与 `_run_one` 附近）。

### 影响面与风险

- 若某处场景实例化时忘了注入，`care_once()` 会静默跳过（记日志）—— 表现为"体力不足被拦截后没有自动护理"。**建议初期保留 `care_fn is None` 时的告警日志，观察一轮再收紧。**
- 环断开后，可以试着 `python3 -c "import src.scenario"` 验证 —— 应当**不再**拉起 scenarios。

### 验收标准

```bash

python3 -c "import sys; import src.scenario; print('scenarios' in sys.modules)"   # 期望 False
grep -rn "from scenarios" src/ | grep -v "^src/.*#"                                 # 期望空
```

### 回归风险点

- `src/scenario.py` 里可能还有其他对 scenarios 的隐式依赖（如有，一并处理）。先跑一遍 `grep -rn "scenarios" src/`。

## B. "什么算今日完成" 有 5 份实现

### 问题

| # | 位置 | 职责 |
| --- | --- | --- |
| 1 | `runner.py:1137-1149`（legacy） | 主循环内联的时长判断 |
| 2 | `runner.py:1652-1690` `_school_due()` | 学习是否可执行 |
| 3 | `runner.py:1699-1766` `_main_choice()` | 主任务组本轮该执行哪个 |
| 4 | `runner.py:2235-2247`（`_write_queue_status` 内部） | **界面显示用**的完成态重算 |
| 5 | `runner.py:2378-2393` `_main_finished()` | 主任务组今天是否全部结束 |

第 4 处最危险：它是**表现层**在重算业务判定。`_write_queue_status()` 为了给仪表盘写"今日完成"标记，自己实现了一遍"疲劳/配额/时长"三连判定。

后果：改"学习到什么程度算今日完成"，要同时改 5 处。漏掉第 4 处的表现是：**界面上某个任务显示"今日完成"（灰掉不执行），但调度器其实还会执行它** —— 或者反过来，最典型的是"改完规则后，界面说还能学、调度器不学"。

### 修复

**收敛到单一实现**，其余改为调用：

```python
# runner.py —— 单一判定入口（以 _main_finished 为基础扩展）
def _task_done_today(self, key: str, tasks: dict) -> bool:
    """**唯一**的"某主任务今日是否已完成"判定。所有消费点（界面/调度/日志）都调它。"""
    ...
```

改造顺序（**分三步，每步可独立验证**）：

**步骤 1（先加不删，0.5 天）**：新增 `_task_done_today()`，让它委托现有逻辑中最完整的那份（`_main_finished` 的口径）。此时**无行为变化**。

**步骤 2（写等价性测试，0.5 天）**：构造 6~8 组边界输入（学习满/未满、打工满/未满、合计达 8h/12h、金币不足、冒险次数满），断言新旧实现**逐组同结果**。

```python
# tests/test_task_done_equivalence.py（示意）
CASES = [
    dict(study_s=7*3600, work_s=0, coins=999, expect=..., label='学习未满'),
    dict(study_s=8*3600, work_s=0, coins=999, expect=..., label='学习满'),
    dict(study_s=6*3600, work_s=2*3600, coins=999, expect=..., label='合计 8h 达限'),
    dict(study_s=4*3600, work_s=0, coins=0,   expect=..., label='金币不足'),
    # ...
]
def test_equivalence():
    for c in CASES:
        assert new_impl(c) == old_impl(c), c['label']
```

**步骤 3（逐个切消费点，0.5 天）**：把 5 处逐个改为调用 `_task_done_today()`，每切一处跑一次等价性测试 + 手动确认界面。

**风险控制**：`expect` 值需先用**当前实现**跑出来填（这就是"锁住现状"），而不是凭理解填 —— 否则会把"现状的 bug"当成正确值固化，或把"正确的期望"当成现状。

### 影响面与风险

- `_write_queue_status`（2181-2356）是**仪表盘契约的写入点**（字段被 `dashboard.py` 读取）。改它内部的判定时**不要动字段名**。
- 疲劳档常量（`DEFAULT_EFFICIENCY_TIERS`、`daily_hour_limit`、`work_stop_hours`）在两处定义（`runner.py` 与 `dashboard.py:408`），`dashboard.py` 的注释自陈"保持一致"—— 这也是双写，建议一并收敛（`dashboard.py` 改为从 `runner` 导入或读配置）。

### 验收标准

1. 等价性测试全绿（步骤 2 完成后）。
2. `grep -c "_load_durations()" scenarios/runner.py` 的使用点数量显著下降（理想是集中在 1 个判定函数里）。
3. 手动构造"学习满 8h"场景，确认**界面显示**与**调度器行为**一致。

### 回归风险点

- 主任务组互斥逻辑（`_main_choice`）依赖这些判定。改动时**逐个消费点切换**，不要一次全改。
- 队列状态文件是跨进程契约，改动后跑 07 文档的契约测试。

## C. 四态无单一真源

### 问题

"进行中 / 结算 / 被雇佣 / 空闲"四种状态的判定有 **4 份实现**：

| # | 位置 | 特点 |
| --- | --- | --- |
| 1 | `scenario.py:1170-1196` `_classify_busy_screen()` | **口径最全**（结算页优先，再 school/work/adventure/employed） |
| 2 | `scenario.py:560-580` `_is_settlement_screen()` | 纯判定，无副作用 |
| 3 | `scenario.py:1105-1132` `_detect_settlement()` | 带副作用（记收益、计雇佣次数） |
| 4 | `dashboard.py:366-405` `work_eta()` | **从日志文本反推**（见 07 文档 C 节） |

**消费点 12 处**：`scenario.py` 的 541 / 897 / 921 / 984 / 1197 / 1252、`scenarios/school.py:163`、`work.py:288`、`adventure.py:76`、`hire_friend.py:278`、`employed.py:39`、`runner.py:1817`。

**状态载体是自由 dict**：`scenario.py:362` 的 `self.pending`，字段由 `defer_busy_end`（921）组装，队列引擎读 `pend['until']`（`runner.py:1858`）。

同一事实存在**三份副本**：内存 `pending`、`runs/queue_status.json`（字段见 `src/queue_status.py`）、日志行。失同步即历史 bug（"宠物被送去上课、我手动召回，停掉调度器再启动，显示还是在上课"就是这么来的）。

### 修复

**引入 `Activity` dataclass 取代自由 dict**，并把"纯判定"与"副作用"分层。

```python
# src/activity.py（新增）
from dataclasses import dataclass, asdict
from typing import Literal, Optional

Kind = Literal['school', 'work', 'adventure', 'employed']

@dataclass(frozen=True)
class Activity:
    """宠物当前活动的单一真源。

    不可变（frozen）：状态变化一律产生新实例，避免"某处改了 dict 字段、别处不知道"。
    """
    kind: Kind
    until: float                      # 结束时间戳（epoch 秒）
    read_at: float                    # OCR 读到剩余时间的时刻（见 runner._defer_busy 的历史坑）
    source: str                       # 来自哪条路径：defer_busy_end / probe_activity_state / _detect_settlement
    note: str = ''                    # 展示用备注

    @property
    def remaining(self) -> float:
        import time
        return max(0.0, self.until - time.time())

    def to_dict(self) -> dict:
        return asdict(self)

    @classmethod
    def from_dict(cls, d: dict) -> 'Activity':
        """兼容读：老格式（自由 dict）→ dataclass。过渡期用。"""
        return cls(
            kind=d['kind'], until=float(d['until']),
            read_at=float(d.get('read_at', d['until'])),
            source=d.get('source', 'legacy'), note=d.get('note', ''),
        )
```

迁移顺序（**每步可独立验证**）：

1. **加 dataclass，不动现有代码**（0.5 天）—— 零行为变化。
2. **`defer_busy_end` / `finish_pending` 内部改用它**，对外仍暴露 `.to_dict()` 给队列状态写入（0.5 天）。
3. **合并判定**：把 `_is_settlement_screen` 与 `_detect_settlement` 的重复口径合一 —— **拆成"纯判定"与"副作用"两层**：
   ```python
   def classify(screen) -> ScreenKind | None:   # 纯函数，可单测
       ...
   def on_settlement(kind, screen) -> None:     # 副作用：记收益、计数
       ...
   ```
4. **消费点逐个切换**（1 天）—— 12 处，每处跑一次回归。

### 影响面与风险

- `probe_activity_state` / `wait_busy_end` 被 4 条调度路径依赖（`runner.py:1817`、`school.py:163`、`work.py:288`、`adventure.py:76`），**签名变更会全线崩** —— 步骤 2 保持对外接口不变只换内部表示。
- `finish_pending` 的 `on_finish` 是闭包注册，换数据结构时回调语义必须保持。
- **先跑 `tools/test_state_freshness.py` 建立基线**（它覆盖队列状态 starting/stopped/pid 判定、`work_eta` 截断、`probe_activity_state`、`wait_busy_end` 重构不变性）—— 这是本项目现存的唯一相关测试，改这块钱必须用它兜底。

### 验收标准

```bash

```

1. 四态判定收敛到**一处纯函数** + 一处副作用处理。
2. `grep -rn "_is_settlement_screen\|_detect_settlement" src/ scenarios/` 的使用点显著减少。
3. 手动复现历史 bug 场景：上课中 → 手动召回 → 停调度器 → 重启，界面**不再**显示"上课中"。

## D. legacy 引擎：不可达，但必须维护

### 问题

`config.yaml:225` 当前是 `engine: task_queue`。

**legacy 专用方法只有 4 个**（脚本比对）：`runner.py:403` `_hire_merged_into_work`、`507` `_eff_tier_hint`、`733` `_reschedule`、`740` `_wait_for_deferred`。

其余 **22 个方法被队列引擎复用**（如 `run_one` 684、`recover` 796、`reload_config` 823、`run` 968）。

**重复实现对照**：

| 职责 | legacy | 队列引擎 |
| --- | --- | --- |
| 异常兜底 | `1236-1237` | `1490-1492`（**逐字相同**） |
| 启动进宠物页 | `948-951` | `1448-1451` |
| 跨天清死标记 | 局部变量 `sched_day`（975 起） | `_rollover_dead_flags` 1538-1564 |
| 退避 | `_reschedule` 733-741（`SIDE_TASK_RETRY_DELAY`=1800，见 `runner.py:137`） | `_fail_task` 2153-2158 |
| 等待 | `_wait_for_deferred` 740-757 | `_sleep_until_next` 2450-2496 |
| 主任务顺序 | 内联 if 链 1030-1230 | `MAIN_TASK_KEYS` + `_main_choice` 1699-1766 |

### 决策建议

**推荐：保留代码，但"软废弃"—— 明确标注 + 不再接受功能更新。**

理由：

1. **删掉的代价高**：legacy 主循环 `Runner.run()` 968-1239（272 行）与 4 个专用方法只占约 350 行，但它们**长在 1059 行的 `Runner` 类里** —— 删它们要动类结构，风险与收益不成比例。
2. **保留的代价可量化且低**：真正的问题是"每次改 `run_one`/`recover`/`reload_config` 都要双路径验证"。但实测这 3 个方法**两种引擎共用同一份代码**（不是两份实现），所以验证成本没有想象中高。
3. **真正的重复只有上表那 6 组**：可以逐个把 legacy 侧的重复块改为调用共用实现，从而消除"两份要保持一致"的负担 —— **这比删引擎更划算**。

**具体步骤**：

1. 在 `Runner` 类与 `run()` 顶部加醒目注释：`# legacy 引擎：当前 config 用 task_queue，本路径仅作历史保留，不再接受新功能；改共用方法时两条路径都要跑一遍。`
2. **消除 6 组重复**：把 legacy 侧的重复块改为调用队列侧的实现（或抽公共函数）。特别是 `1236-1237` 与 `1490-1492` 这种**逐字相同**的，直接抽一个 `_handle_scenario_error()`。
3. 在 `AGENTS.md` 记录决策：若未来 3 个月无人使用 legacy，再评估删除（届时 `Runner` 类可整体收缩）。

**不推荐直接删**：删了以后如果用户想回退引擎（`runner.engine: legacy`），功能就没了；而这条路径的存在本身就是"可回退"的保障。

### 验收标准

1. 6 组重复块消除后，`grep -c "SIDE_TASK_RETRY_DELAY" scenarios/runner.py` 只剩常量定义 1 处。
2. 两种引擎各跑一次冒烟（`--test` 模式 + 手动切 `config.yaml` 的 engine）。

### 回归风险点

- legacy 路径**无法在自动化测试里覆盖**（需要真机）。改动 6 组重复块时，至少确认"改动处两条路径走的是同一逻辑"。

### 路由表改造示例（`do_GET` 146 行 → 声明式）

```python
# 现在：146 行的 if/elif 链（dashboard.py:1542-1687）
# 改为：
GET_ROUTES: list[tuple[str, Callable[[Handler, str], None]]] = [
    ('/',              handle_index),
    ('/manifest.json', handle_manifest),
    ('/sw.js',         handle_sw),
    ('/api/data',      handle_api_data),
    ('/api/logs',      handle_api_logs),
    # ...
]

def do_GET(self):
    u = urlparse(self.path)
    path = u.path
    for prefix, handler in GET_ROUTES:
        if path == prefix or path.startswith(prefix + '/'):
            handler(self, path)
            return
    self._send(404, 'text/plain; charset=utf-8', b'not found')
```

好处：新增 API 只加一行，不再改 146 行的热点函数（当前任何并发改动都会在这里冲突）。

## G. 表现层混进调度器

### 问题

`runner.py:2181-2356` 的 `_write_queue_status()` 自己重算任务完成态（2235-2247 的疲劳/配额/时长三连判定），与以下四处并列成**第 4、5 份实现**：

- `_eligible` 1589
- `_task_due` 1772
- `_main_choice` 1699
- `_main_finished` 2378

后果：改"什么算今日完成"要同时改 5 处，漏一处就是**界面显示"可执行"但调度器不执行**（或反之）的哑火。

### 修复

`_write_queue_status()` 只做**序列化**，不做事判定：

```python
# before（2235-2247 附近，内联判定）
elif key == 'school':
    study_s, work_s = self._load_durations()
    if ...:   # 重算疲劳/配额

# after
elif key == 'school':
    done = self._task_done_today('school', tasks)   # 调单一实现（B 节）
```

### 验收标准

```bash
grep -n "_load_durations()" scenarios/runner.py    # 期望：集中在判定函数内，不在 _write_queue_status 里
```
