### 风险场景（具体触发条件 → 后果）

**最要紧的是 `queue_status.json`**：dashboard 每 6 秒读一次，而调度器每轮调度都写。

1. 调度器执行 `json.dumps` + `write_text`（内核里是 `open(truncate)` → `write`），**中间存在一个"文件已被截断、内容还没写完"的窗口**
2. 若 dashboard 恰好在此窗口内读取 → 拿到空文件或半截 JSON
3. `dashboard.py` 的 `read_json` 有异常兜底（返回 `{}`），所以**不会崩**
4. 但界面会瞬间显示"队列为空 / 无当前任务"，然后 6 秒后恢复

**这类闪现在实测中难以复现**（窗口通常 <1ms），但一旦发生，用户看到的是"任务列表突然空了"。更糟的是如果 JSON 被截断在字段中间，`read_json` 返回 `{}` 后前端按"无数据"渲染，**可能触发一次多余的重排或状态跳变**。

### 修复

**抽出公共原子写工具**，5 处统一改用。

```python
# src/jsonstore.py（新增）
"""跨进程共享的 JSON 文件读写：统一原子写，避免消费端读到半截内容。

背景：runs/ 下的文件被调度器子进程与 dashboard 进程同时读写（见
docs/review/07-进程间契约.md）。裸 write_text 存在"截断后未写完"的窗口，
消费端会读到空/半截 JSON —— 虽然 read_json 有兜底不会崩，但界面会闪现空状态。
"""
import json
import os
from pathlib import Path
from typing import Any


def write_json(path: Path, data: Any, *, indent: int | None = None) -> None:
    """原子写：先写同目录 .tmp 再 os.replace（同文件系统内 rename 是原子的）。"""
    path.parent.mkdir(parents=True, exist_ok=True)
    tmp = path.with_name(path.name + '.tmp')
    tmp.write_text(
        json.dumps(data, ensure_ascii=False, indent=indent), encoding='utf-8')
    os.replace(tmp, path)


def append_jsonl(path: Path, record: dict) -> None:
    """append 语义（jsonl）。用 O_APPEND 保证单次写入的原子性 —— 
    小于 PIPE_BUF 的写入在 POSIX 下对 append 打开的文件是原子的，跨进程不会交错。"""
    path.parent.mkdir(parents=True, exist_ok=True)
    line = json.dumps(record, ensure_ascii=False) + '\n'
    with open(path, 'a', encoding='utf-8') as fh:
        fh.write(line)
```

**逐处改法**：

```python
# src/queue_status.py:71-72
# before
QUEUE_STATUS_FILE.write_text(json.dumps(state, ensure_ascii=False), encoding='utf-8')
# after

write_json(QUEUE_STATUS_FILE, state)

# src/status_cache.py:59-60
write_json(STATUS_CACHE_FILE, data, indent=2)

# src/hire_quota.py:54-55
write_json(HIRE_QUOTA_FILE, {'date': today, 'mins': mins})

# scenarios/visit.py:106
write_json(FRIENDS_CACHE_FILE, {'names': merged, ...})

# scenarios/pk.py:356-357
write_json(HELPER_STATE_FILE, {'name': name, 'source': source, 'at': ...})
```

**顺带**：`src/progress_store.py:73-77` 与 `src/instance.py:89-91` 的实现与新工具**完全重复**，一并改为调用（消除三份拷贝）。

### 影响面与风险

- `os.replace` 要求 tmp 与目标在**同一文件系统**。当前都写在 `runs/` 下，满足。
- `.tmp` 残留：进程若在 `write_text` 与 `os.replace` 之间被杀，会留下 `.tmp` 文件。建议在启动时清理 `runs/*.tmp`（`progress_store.py:56` 已有把损坏文件备份为 `.corrupted.bak` 的先例）。
- 原子写**不解决并发覆盖**（两个进程同时写同一文件，后写赢）—— 但这些文件都是单写者（调度器写、dashboard 读），所以够用。

### 回归风险点

- 改 `queue_status.py` 后，**仪表盘会立刻读新格式**（字段名不变，所以兼容）。但调度器与 dashboard 若版本不一致（一个改了、一个没重启），行为仍正常（格式未变）。
- **不要给 `.tmp` 文件加时间戳后缀**，否则并发写会留下多个临时文件；固定后缀 + `os.replace` 是标准做法。

## C. 日志文案当契约（**最致命**）

### 问题

`dashboard.py:350`：

```python
RUN_START_LOG_RE = re.compile(r'调度引擎:\s*(?:task_queue|legacy)')
```

`dashboard.py:366-405` 的 `work_eta()` **用正则解析调度器日志里的中文文案**，反推"宠物现在在干什么"：

```python
"""从日志里找最后一次"进行中"登记，算出剩余秒数 + 场景名（kind）。

**两种日志格式都要认**（都代表"已登记 pending、先调度其他任务"，只是来源不同）：
  ① `冒险: 进行中，预计 44 秒后结束（…收尾）` —— scenario.defer_busy_end
  ② `检测到正在打工，预计 2681 秒后结束（…收尾）` —— scenario.detect_busy_remaining
早期只匹配 ①，导致手动切到打工后界面仍停在更早那条"冒险: 进行中"上——
而那条的结束时间早过了，于是显示"冒险中 / 收尾中"（用户实报的 bug）。
"""
```

**注释里的"（用户实报的 bug）"就是这套机制的代价证明。**

**为什么这是致命缺陷**：

- 两个进程之间的**核心状态传递**，靠的是**匹配中文日志文案**
- `scenarios → dashboard` 的 import 是 0 条（进程隔离做对了），代价是**契约退化为文本**
- **改一句日志文案，仪表盘状态条就静默失准** —— 不报错、不崩溃，只是显示错的

举例：若有人把 `f'冒险: 进行中，预计 {n} 秒后结束'` 改成 `f'[冒险] 进行中，约 {n} 秒后结束'`，`work_eta()` 立即失配 → 界面永远显示"等待中"。而改日志的人**不会知道**自己破坏了什么。

### 修复（根治）

**调度器直接写状态文件**，dashboard 读文件而非解析日志。

**步骤 1：扩展 `queue_status.json` 的字段**（`src/queue_status.py`）

```python

{
  "pid": 25355,
  "started": 1759999999.0,
  "state": "running",
  # ... 现有字段 ...

  # ↓ 新增：当前活动（替代 work_eta 的日志正则）
  "activity": {
    "kind": "adventure",           # school | work | adventure | employed | null
    "until": 1760000123.4,         # 结束时间戳（epoch 秒）
    "read_at": 1760000043.4,       # OCR 读到剩余时间的时刻
    "source": "defer_busy_end",    # 哪条路径登记的（排查用）
    "note": "附近走走"
  },
  "activity_reason": "想雇的「墨瞳」正打工中，稍后重试"   # 即现有 next_reason 的语义

```

**步骤 2：写入点**（`src/scenario.py` 的 `defer_busy_end` / `finish_pending` / `_detect_settlement`，以及 `runner.py` 的 `_write_queue_status`）

在登记/清除 pending 时同步写 `activity` 字段：

```python

# finish_pending() 内，收尾完成后
```

**步骤 3：消费点改造**（`dashboard.py`）

**步骤 4：过渡期（灰度）**

- 调度器**同时**写 `activity` 字段**和**打原来的日志（两者并存 1~2 个版本）

- 这是跨进程契约变更，**dashboard 与调度器必须能独立升级**（新旧组合都要能跑）—— 所以字段可选 + 回退分支是必需的，不能直接删日志解析。
- 前端的 `work_eta` 展示逻辑（`Deck.tsx` 的 `remain`/`etaKind`）依赖返回三元组，改返回值结构要同步。

## D. 无 schema、无版本号

### 问题

**schema 有两份拷贝**：

- `src/queue_status.py:36-115`（生产者的"权威"定义）
- `dashboard.py:52-62`（本地兜底复制，`mark_starting` 之类）

改一个字段要改两处。且**没有任何版本号** —— 老 dashboard 读新调度器写的文件，行为未定义。

### 修复

**单一 schema 声明 + 版本号**：

```python
# src/queue_status.py
SCHEMA_VERSION = 2      # +1 表示字段语义有不兼容变化；dashboard 据此判断能否解析

def build_state(...) -> dict:
    return {
        '_schema': SCHEMA_VERSION,
        ...
    }
```

```python
# dashboard.py 消费端
SCHEMA_VERSION_SUPPORTED = 2

qs = read_json('queue_status.json')
v = qs.get('_schema', 1)          # 缺省视为 v1（老调度器）
if v > SCHEMA_VERSION_SUPPORTED:
    # 调度器比 dashboard 新：只读能理解的字段，界面给出提示
    log_once('队列状态 schema 较新（%s > %s），部分信息可能不准确' % (v, SCHEMA_VERSION_SUPPORTED))
```

**并消除 `dashboard.py:52-62` 的本地复制**：改为从 `src.queue_status` import 构造函数。

### 影响面与风险

- 加 `_schema` 字段对老消费端无害（多一个未知 key）。
- `dashboard.py` import `src.queue_status` 是否会拉起重依赖？`queue_status.py` 很小（5743 字节），只依赖 stdlib + 路径常量，安全。

### 验收标准

1. `grep -c "queue_status" dashboard.py` 的重复定义消失。
2. 手动把 `_schema` 改成 `99` → dashboard 打印一次提示且不崩。

## E. 新鲜度判定机制的脆弱性

### 问题

`src/queue_status.py` 的这套机制：

```python
src/queue_status.py:105    STARTUP_PLACEHOLDER_GRACE_SECONDS = 600
src/queue_status.py:119        return age_seconds < STARTUP_PLACEHOLDER_GRACE_SECONDS
```

配合 `status_is_current()` / `startup_placeholder_active()` / `mark_starting()` / `mark_stopped()`，靠 **PID + 日志行 + 时间戳** 判断"这份状态是不是当前这个进程写的"。

> **更正一处此前的误判**：我最初认为 `AGENTS.md` 里"启动中宽限期 600s"与"超过 10 分钟宽限期"是文档自相矛盾。**实测代码 `queue_status.py:105` 是 `600`，600 秒就是 10 分钟 —— 两种说法是同一个值的不同表述，不矛盾。** 这里没有 bug。

真正的失效场景：

| 场景 | 触发条件 | 后果 | 加固 |
| --- | --- | --- | --- |
| **PID 复用** | 调度器崩溃退出，OS 把同一 PID 分给另一个进程 | `status_is_current()` 误判为"当前进程写的"，界面显示陈旧的"上课中" | 同时校验 `started` 时间戳与 `runner.pid` 文件；或用「PID + 进程启动时刻」双因子（`psutil` 无依赖替代：读 `/proc/<pid>/stat` 的 starttime，macOS 用 `ps -o lstart=`） |
| **时钟回拨** | NTP 校时 / 手动改表导致 `now < started` | `age_seconds` 变负 → `status_is_current` 判断异常 | 对 `age_seconds < 0` 视为"不可信"，退回"启动检查中" |
| **日志轮转** | `runs/logs/` 跨天切文件（`today_log_path()`） | `lines_since_runner_start()` 在新文件里找不到 `RUN_START_LOG_RE` → 认为"没有启动记录" | 已由 `mark_starting()` 写 PID 兜底；但要确认两条路径都覆盖 |
| **跨天** | 调度器连续跨零点运行 | 日志文件切换，同上 | 同上 |
| **跨机器** | dashboard 与 runner 不在同一台机器（README 明确说不支持，但无技术阻止） | PID 语义完全失效，读到的是别人机器的 `runs/` | 在状态文件里加 `host` 字段，不匹配则拒绝判定 |

### 修复（按风险排序）

**E1（PID 复用，最值得做）**：

```python
def _process_start_time(pid: int) -> float | None:
    """取进程启动时刻（秒）。macOS/Linux 通用：ps -o lstart= -p <pid> 解析；
    失败返回 None（调用方退回单 PID 判定）。"""
    import subprocess
    try:
        out = subprocess.run(
            ['ps', '-o', 'lstart=', '-p', str(pid)],
            capture_output=True, text=True, timeout=2)
        if out.returncode != 0 or not out.stdout.strip():
            return None
        import email.utils, time as _t
        return _t.mktime(email.utils.parsedate(out.stdout.strip()))
    except Exception:
        return None
```

把 `started` 与进程真实启动时刻对比（容差 5 秒），不一致 → 视为陈旧。

**E2（时钟回拨）**：

```python
def status_is_current(...) -> bool:
    ...
    if age_seconds < 0:
        # 时钟回拨或文件来自未来：不可信，退回占位态
        return False
```

**E3（跨机器）**：状态文件加 `host` 字段（`socket.gethostname()`），不匹配时拒绝判定。

### 验收标准

1. 手动改 `queue_status.json` 的 `pid` 为当前 dashboard 的 PID（伪造）→ 应**仍被判定为陈旧**（靠 `started` 双因子）。
2. 把 `started` 改成一个未来时间 → 判定为"不可信"而非"新鲜"。
3. `python3 tools/test_state_freshness.py --no-gui` 全绿（这个脚本覆盖了 starting/stopped/pid 判定）。

### 回归风险点

- `ps` 在 Windows 上语法不同（`ps -o lstart=` 不支持）。本项目声明支持 Windows（README），**要么用跨平台方案，要么把 E1 限定在非 Windows**（`sys.platform != 'win32'`）。
- 改这套判定逻辑**必须**跑 `tools/test_state_freshness.py` —— 它是为这块逻辑专门写的。

## S2. 非原子写：从 5 处补到 9 处

### ① `dashboard.py:54-60` —— **dashboard 也是 queue_status.json 的写者**（最严重）

上文 F 节建议重组 `runs/` 目录结构。第二轮核查的结论更保守、也更务实：

> **只对新增文件定规范，存量不改名。**

理由：重命名需要**两个进程同时上线**（否则一方读旧名、一方写新名），收益远小于风险。

规范建议：

- 新文件命名 `<子系统>.<用途>.json`
- `.signal` 只用 mtime，内容无意义（现状：内容是时间戳但语义在 mtime）
- 临时文件统一 `<name>.tmp`（现状有 `.tmp` 与 `.json.tmp` 两套）

**并且发现 `runs/` 根目录混放**：26.9MB 控制台日志 + 截图产物 + 状态文件，需要分层（至少把日志与产物移出根目录）。

## S8. 三路线代价评估（结论）

| 路线 | 判定 | 理由 |
| --- | --- | --- |
| **Unix domain socket** | **不做** | 手机端是 HTTP 轮询，还要加 HTTP 桥；丢掉 `cat`/`grep` 的可调试性 |
| **SQLite** | **中期可选，当前不做** | 破坏 `fatigue.py:10` 明写的"删文件即恢复"运维路径；且只对 `session_rewards` 聚合有意义 |
| **纯文件增量改良** | **采纳** | 即本文方案 |
