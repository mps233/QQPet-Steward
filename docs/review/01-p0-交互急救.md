### 前置事实（后面四条都要用到，先核实清楚）

- `--u` 的真实定义在 `web/src/styles/app.css:115`：`--u:var(--vu, calc(100vw / 360));`
  由 `web/src/lib/stage.ts:11` 写入 `--vu = clientWidth / 360 px`。
  所以 **1u = 屏宽/360**；390px 屏上 1u ≈ 1.083px。
- `.drawer` 实际宽度 `62u` → 390px 屏上 **≈ 67.2px**，360px 屏上 **62px**。
- 总览页的滚动容器是 `section.home` 自己（`web/src/styles/app.css:1555` 的注释已写明），
  `.home` 内的浮动层全是 `position:absolute`。
- `.scene`（任务卡列）：类规则起于 `web/src/styles/app.css:680`，其中坐标是
  `web/src/styles/app.css:693` 的 `left:calc(var(--u) * 74);` 与
  `:694` 的 `width:calc(var(--u) * 207);`
  → 390px 屏上 left ≈ 80.2px，**右缘 = (74+207)u = 281u ≈ 304.4px**，右侧留 22u 给功能栏。
- `#torderToast` 是 `position:fixed; bottom:40u`（`web/src/styles/app.css:965`），
  `.deck` 底栏高 `135u`（`web/src/styles/app.css:775`）→ **toast 落在底栏内部，直接压住状态卡**。

## 缺陷 1 · 状态卡信息被 CSS 关掉

### ① 问题描述

三处证据，全部实测：

**1a. 宽度只给 62u。** `web/src/styles/app.css:797-800`（现状原文）：

```css
  left:50%;
  transform:translateX(-50%);
  top:calc(var(--u) * 12);
  width:calc(var(--u) * 62);
```

这个盒子里要装的东西（`web/src/components/Deck.tsx:93-122`）：44×46u 的图标、
14u 的状态词、hint 一句、**两句** `.dsub`、一个 `.saveMsg` 槽位、以及 `.dmeta`。
390px 屏上 67.2px 宽，`.dsub` 又是 `white-space:nowrap` + `text-overflow:ellipsis`
（`web/src/styles/app.css:828-832`）→ 文案全部被省略号吃掉。

**1b. `.dhint` 整条被关掉 —— 剩余时间在这里消失。** `web/src/styles/app.css:827`：

```css
.dhint{display:none}
```

对应 `web/src/components/Deck.tsx:107-109`：

```tsx
            <span className="dhint" id="runnerHint">
              {hint}
            </span>
```

`hint` 在 `Deck.tsx:65-71` 计算，其中**唯一**给出「剩余 hms(remain)」的分支就是
`Deck.tsx:67-68` 的 `busyEta ? \`剩余 ${hms(remain ?? 0)}\``。
`display:none` 让 `remain`（`Deck.tsx:43`，来自 `data.work_eta.remaining`，
类型见 `web/src/api.ts:38-43`）**在界面上完全不可达**。这是本缺陷最严重的一处：
后端一直在算剩余时间，前端把它渲染出来又用 CSS 关掉。

**1c. `.dmeta` 整条被关掉 —— PID / 已跑时长消失。** `web/src/styles/app.css:833`：

```css
.dmeta{display:none}
```

对应 `web/src/components/Deck.tsx:119-121`：

```tsx
        <span className="dmeta" id="runnerMeta">
          {running ? `PID ${sch.pid}${sch.uptime ? ` · 已跑 ${sch.uptime}` : ''}` : '未运行'}
        </span>
```

**1d. 附带问题：`hint` 与 `sub` 内容重复。** `Deck.tsx:79` 在 `busyEta` 分支下
`sub` 已经写了 `剩余 ${hms(remain ?? 0)} · 结束后自动开启下一项`，与 `Deck.tsx:68` 的
`hint` 同一份数据。恢复 `.dhint` 前必须先消掉这个重复，否则同一秒数会并排出现两次。

**1e. 另一个真实约束：`.deck` 只给 123px 可用高度。**
`web/src/styles/app.css:789-791` 的注释是实测记录：360px 视口下 `.drawer` 内容高 121px，
而 `.deck` 只给 `135u - 12u(top) = 123px`。**恢复 `.dhint` + `.dmeta` 会让内容高增长
~24px，必然再次溢出 121→123 的余量**，触发 `.home` 可滚（就是那段注释里用户实报的
"底栏最下面有一块很细很细的区域，导致可以滚动一点点"）。所以本方案**不能只是把
`display:none` 去掉**，必须同时把布局从"竖排居中"改成"横排"——横排才是真正解决宽度
问题的做法，也让高度回到单行。

### ② 修复方案

#### 步骤 1：改布局为横排 + 整宽（`app.css:785-836` 整段替换）

替换 `web/src/styles/app.css` 第 **785-836** 行（`.drawer{` 到 `.dot.off{...}` 这两行之间，
不含 `.dot` 那三行）为：

```css
.drawer{
  /* 底部信息：坐在 .deck 弧形面板上。
     宽度从 62u 放到 281u = .scene 任务卡列的右缘（74u + 207u），
     左侧与左列圆钮右缘（20u + 42u = 62u）留 12u 缝。
     横排：[图标] | [状态 / 原因 / 剩余·下一步 三行文本]。 */
  left:calc(var(--u) * 62);
  right:calc(var(--u) * 22);
  width:auto;                     /* 覆盖旧的 width:62u，用 left/right 定宽即可自适应 */
  transform:none;                 /* 旧的 translateX(-50%) 必须撤掉，否则整块左移半个身位 */
  top:calc(var(--u) * 10);
  display:flex;
  flex-direction:row;             /* 竖排 → 横排：这是高度不溢出的关键 */
  align-items:center;
  gap:calc(var(--u) * 8);
  background:transparent;box-shadow:none;
  text-align:left;                /* 竖排时是 center，横排必须改回 left */
}
.dico{
  width:calc(var(--u) * 34);height:calc(var(--u) * 36);   /* 44×46 → 34×36，给文本让出水平空间 */
  object-fit:contain;flex:none;
}
.dcol{
  display:flex;flex-direction:column;align-items:flex-start;
  gap:calc(var(--u) * 1);
  min-width:0;                    /* flex 子项省略号的必要条件：不给 0 就撑破父级 */
  flex:1;
}
.dtitle{
  display:flex;align-items:center;gap:calc(var(--u) * 3);
  font-weight:680;font-size:calc(var(--u) * 14);color:var(--strong);
  white-space:nowrap;
  /* 状态灯仍绝对定位到文字左侧（否则 flex 居中被灯宽推偏，旧注释的实测偏差 5px） */
  position:relative;
  padding-left:calc(var(--u) * 11);
}
.dtitle .dot{
  position:absolute;left:0;
  top:50%;transform:translateY(-50%);
}
.drow{display:contents}

/* 第 ③ 行：剩余 / 下一步。**原来是 display:none，本缺陷的核心**。
   字号 11u（行 ① 14u、行 ② 11u、行 ③ 11u，即需求里的三行结构）。
   tabular-nums 让倒计时每秒跳动时数字不抖。 */
.dhint{
  display:inline-block;
  font-size:calc(var(--u) * 11);
  color:var(--sub);
  font-variant-numeric:tabular-nums;
  white-space:nowrap;overflow:hidden;text-overflow:ellipsis;max-width:100%;
}
.dsub{
  font-size:calc(var(--u) * 11);
  color:var(--sub);
  font-variant-numeric:tabular-nums;
  white-space:nowrap;overflow:hidden;text-overflow:ellipsis;max-width:100%;
}
.dmeta{
  /* **原来是 display:none**。横排后放回行 ③ 尾部，字号再压一档、颜色更淡，
     让它退到信息层级最底层（PID 是排查用，不是日常信息）。 */
  display:inline-block;flex:none;
  font-size:calc(var(--u) * 9);
  color:var(--sub);opacity:.7;
  font-variant-numeric:tabular-nums;white-space:nowrap;
}
.dot{width:calc(var(--u) * 7);height:calc(var(--u) * 7);border-radius:50%;background:#9ca3af;flex:none}
.dot.on{background:var(--ok)}
.dot.off{background:#ef4444}
```

> ⚠️ `.drawer` 用 `left` + `right` 定宽后**必须显式写 `width:auto`**。
> 只删 `width` 不够——`app.css` 里 `.drawer` 是独立的类规则，没有其它同族规则会去覆盖它，
> 但保留 `width:calc(var(--u)*62)` 与 `left/right` 同时存在时，`width` 胜出、
> `right` 变成死代码，你会看到"改了没生效"。

### ③ 影响面与风险

- **`.drawer` 是总览页独占的类**（`grep -rn "drawer" web/src/` 只命中 `Deck.tsx:94`），
  改它不影响任何内页。同样 `.dico/.dcol/.dtitle/.dhint/.dsub/.dmeta` 均只在 `Deck.tsx` 出现。
- **`.dtitle` 的 `justify-content` 被移除**：旧值是 `center`，配合 `.drawer` 的
  `align-items:center` 把文字居中在图标下方。横排后左对齐是正确形态，但**这会改变
  状态词的视觉位置**——改完必须看真机截图确认不是"偏左看着别扭"。这是本方案唯一
  的主观项，若用户要求保持居中，把 `.dcol` 的 `align-items:flex-start` 改回 `center`
  并把 `.dtitle` 的 `padding-left:11u` 去掉即可（宽度问题仍由整宽解决）。
- **高度**：横排 + 图标降到 36u 后，`.drawer` 内容高预估从 121px 降到约 74px
  （图标 36u ≈ 39px + gap + 三行 ≈ 14+11+11+行距）。`.deck` 可用 123px，
  余量充足。**但这是估算，必须按验收 A5 实测**。
- **`width:auto` + `left/right` 会让 `.drawer` 宽度随视口变**，不再有 62u 的固定值，
  所以 `.dsub` 的 `max-width:100%` 与 `min-width:0` 必须保留，否则长文案撑破父级、
  把整块顶出 `.home` 右缘。
- **不触碰 `.deck` 的 `135u`**：`web/src/styles/app.css:796` 明确写了那是官方底栏的形，别动。

### ④ 验收标准

在 8787 的服务上用同源 iframe（`window-size` 最小 500px，必须用 iframe 才能测窄屏，
见 FRONTEND_PITFALLS 第二节）：

```bash
# 1. 起 iframe 承载页（放 web/dist/assets/ 下：放 / 下会 404）
cat > web/dist/assets/_probe.html <<'EOF'
<!doctype html><html><body style="margin:0">
<iframe src="/" width="390" height="844" style="border:0"></iframe>
</body></html>
EOF
cd web && node node_modules/vite/bin/vite.js build
```

在 iframe 内执行（DevTools 的 frame 上下文，或注入 `<script>`）：

```js
const d = document.querySelector('.drawer')
const u = parseFloat(getComputedStyle(document.documentElement).getPropertyValue('--vu'))
const hint = document.querySelector('.dhint')
const meta = document.querySelector('.dmeta')
const home = document.querySelector('.home')
JSON.stringify({
  drawerW: d.getBoundingClientRect().width,       // 期望 ≈ 281 * u
  drawerR: d.getBoundingClientRect().right,        // 期望 ≈ 390 - 22*u
  hintShown: getComputedStyle(hint).display,       // 期望 "inline-block"，**不能是 none**
  hintText: hint.textContent.trim(),               // 期望含 "剩余 "（有进行中活动时）
  metaShown: getComputedStyle(meta).display,       // 期望 "inline-block"
  homeExtra: home.scrollHeight - home.clientHeight // 期望 0
})
```

- **A1** `drawerW` 在 390px iframe 下 ≈ `281 * 1.0833` ≈ **304.4px**（±2px）。
  360px iframe 下 ≈ 281px。旧值 67.2px，改前先记一遍作为对照。
- **A2** `drawerR` ≈ `390 - 22*1.0833` ≈ **366.2px**，即与 `.scene` 任务卡列右缘对齐。
- **A3** `hintShown` 为 `inline-block`。再手动把 `work_eta.remaining` 造一个非零值
  （临时改 `/api/data` 响应或直接给 `hint` 传常量）确认文本形如
  `剩余 1:59:00 · 21:40 结束 · 之后去做学习`。
- **A4** `metaShown` 为 `inline-block`，且文本含 `PID`。
- **A5** `homeExtra === 0`。**这是最关键的一条**：`.home` 一旦可滚，就是
  `web/src/styles/app.css:789-791` 记录的"底部露出一条细边"缺陷复发。
  若 > 0，按步骤 3 的注释把 `.dstat` 降级为 `display:none` 后重测。
- **A6** 360px 与 390px 两个宽度都要跑，且**必须再跑一遍 `@media(max-width:360px)` 分支**
  （`web/src/styles/app.css:1438`）——FRONTEND_PITFALLS 第四节记过：改基规则但真机
  命中窄屏分支，等于没改。
- **A7** 真机（iPhone）截图确认状态词位置可接受（见 ③ 的主观项）。

### ⑤ 回归风险点

- **FRONTEND_PITFALLS 第一节：高度链**。`.drawer` 是 `.home` 内的 `.flt`（`position:absolute`），
  **它撑不开任何父级**；`min-height:100%` 的链条断在 `.app` / `main` / `.page-slot` 任一层
  就会整页塌成只剩背景。本改动只动 `.drawer` 自身尺寸，**不许给 `.home` 或其祖先加
  `position:relative`**（该节明确记录：加 relative 立刻只剩背景）。改完量 `.home` 高度 ≈ 视口高。
- **FRONTEND_PITFALLS 第四节：`@media` 同名规则**。已在验收 A6 覆盖。
- **`main >` 直系选择器**：本改动不新增容器层级，但步骤 3 引入了 `.dthird` 一层。
  `.dthird` 在 `.drawer > .dcol` 之内，与 `main > section[data-page]` 无关；
  仍建议按该节要求跑 `grep -n "main >" web/src/styles/app.css` 确认无失效。
- **`.saveMsg` 的位置**：`web/src/styles/app.css:1675` 有
  `main section[data-page]:not([data-page="main"]) > .saveMsg` 规则。总览页的
  `.saveMsg` 在 `.drawer` 内、`data-page="main"`，不会被命中；但**别把 `.drawer` 挪到内页**。

## 缺陷 2 · 启动 / 停止请求无 catch，失败静默

### ① 问题描述

**2a. `start()` 只有 `finally`。** `web/src/App.tsx:286-296`（现状原文）：


### ② 修复方案

#### 步骤 1：`api.ts` 的 `runnerStart`/`runnerStop` 改成判 `r.ok` 并按后端契约解析

替换 `web/src/api.ts:181-183`：

```ts
/** 调度器启停（功能栏的两个按钮）。
 *  **后端失败返回 HTTP 400 + `{ok:false,msg}`**（见 dashboard.py 的 /api/runner/start|stop），
 *  旧的裸 fetch 不看 r.ok，四种失败全被吞掉。这里统一收口：
 *  HTTP 层失败用 msg 兜底，网络层失败交给 throw 由调用方 catch。 */
export interface RunnerResult {
  ok: boolean
  msg?: string
  scheduler?: SchedulerInfo
}

async function runnerPost(path: string): Promise<RunnerResult> {
  const r = await fetch(path, { method: 'POST' })
  let body: RunnerResult | null = null
  try {
    body = (await r.json()) as RunnerResult
  } catch {
    body = null   // 后端挂了返回 HTML 错误页，解析失败不能连状态码信息一起丢
  }
  if (!r.ok || !body?.ok) {
    throw new Error(body?.msg || `请求失败 HTTP ${r.status}`)
  }
  return body
}

export const runnerStart = (): Promise<RunnerResult> => runnerPost('/api/runner/start')
export const runnerStop = (): Promise<RunnerResult> => runnerPost('/api/runner/stop')
```

> `scheduler_start()` 返回的 `msg` 已经是中文可读句（`已启动（PID 1234）` /
> `启动后 8 秒内未检测到进程，请看 runs/runner_console.log`），
> **直接透传给用户即可，前端不要再造一套文案**。
>
> ⚠️ **`/api/runner/stop` 在"本来就没在跑"时返回的是 `ok: true`**
> （`dashboard.py:270-271`：`{'ok': True, 'msg': '调度器本来就没有在运行', ...}`），
> 不是错误。所以 `runnerPost` 判 `!body.ok` 对它不成立——这是对的，
> 停止一个已经停了的调度器不算失败。

#### 步骤 2：`App.tsx` 加 `catch`，写持久错误条

先加状态。在 `web/src/App.tsx:210` 的 `const [orderMsg, setOrderMsg] = useState('')`

```tsx
   *  retry 保存失败时该重试哪个动作。 */
```

然后替换 `web/src/App.tsx:286-307` 的 `start` / `stop` 两个函数整体：

```tsx

    setBusy('start')
    setActionErr(null)
    try {

      reload()
```

> 会把一份陈旧数据刷进界面，而错误条与刷新同时发生，用户会看到"错误条 + 看起来正常的状态"，
> 分不清到底成没成功。这是本步骤唯一容易写错的地方。
>

> **当次渲染**的 `start`，这没问题（每次失败都拿到最新版本）。但如果你后续把它们包进
> `useCallback`，**依赖数组要补 `showActionErr`**，否则 eslint 与语义都会偏。

### ③ 影响面与风险

- **`runnerStart` / `runnerStop` 的返回类型从 `Promise<Response>` 变成
  `Promise<RunnerResult>`**。`grep -rn "runnerStart\|runnerStop" web/src/` 只命中
  `App.tsx:2`（import）与 `App.tsx:289,300`（两处 `await`，都不使用返回值）。
  **没有其它调用点**，改签名安全。若将来有人想拿 `Response` 会类型报错，
  这是想要的（`tsc --noEmit` 是硬门禁）。
- **新增"HTTP 400 变成 throw"的行为**：以前 `scheduler_start` 返回
  `{ok:false,msg:'调度器已在运行（PID N），不重复启动'}` 时前端静默；现在会弹红条。
  **这是"已在运行"的正常情况也会弹**。判断是否要为此降级：`alive` 为真时
  `FuncBar.tsx:29` 的 `disabled={alive || !!busy}` 已经禁掉了启动按钮，
  所以用户走不到这个分支——除非两个客户端同时点。**建议保持现状**
  （并发下告知用户"已经在跑"比静默好），但要在验收里确认这条路径的表现。
- **`showActionErr` 的定时器不随组件卸载清理**。`App` 是根组件、生命周期等于页面，
  实际不会卸载；但按现有代码风格（`App.tsx:244` 的 `leaveTimer` 也没清），
  保持一致即可，不额外加 cleanup。**若后续把 `start`/`stop` 下沉到子组件，必须补 cleanup。**
- **`#actionErr` 的 `z-index:100`** 高于 `#torderToast` 的 99
  （`web/src/styles/app.css:968`）与 `#sceneToast` 的 9（`:349`），三层不打架。

- **B3** 单次点击后 5 秒内红条不消失；点红条上的「重试」立即重新发起请求（Network 面板可见）。
- **B4** 断开后端模拟网络层失败：

- **B5** 成功后**不再**出现红条，按钮在 3 秒内保持「启动中」然后按 `alive` 正确落位。

### ⑤ 回归风险点

- **FRONTEND_PITFALLS 第三节：iOS 手势 × 滚动容器**。`#actionErr` 是 `position:fixed`、
  **不在任何滚动容器内**，`onClick` 可靠，不受 `pointercancel` 影响。
  **但如果有人后来把它改成 `position:absolute` 放进 `.home`（一个滚动容器），
  点击就会随机失效** —— 该节记录过完全相同的现象（"圆钮点不开面板，改用 onClick 解决"）。
  所以这里的 `onClick` 是刻意的，不要改成 `onPointerUp`。
- **FRONTEND_PITFALLS 第二节：`env(safe-area-inset-*)` 在 headless 里恒为 0**。
  所以验收 B2-B6 在 headless 里跑只能验证"红条出现 + 文案正确"，
  **顶置位置是否被状态栏吃掉只能靠真机截图**。不要因为 headless 里位置"看着对"就结案。
- **`role="alert"`** 会让读屏软件打断播报。若用户反馈太吵，改成 `role="status"`。

## 缺陷 3 · 停止调度器无确认、与启动零间距

### ① 问题描述

**3a. 点击即停，无任何确认。** `web/src/components/FuncBar.tsx:35-44`（现状原文）：

```tsx
        <button
          className="fab stop"
          id="btnRunnerStop"
          title="停止调度器"
          disabled={!alive || !!busy}
          onClick={onStop}
        >
          <img className="fi" src="/qp-icons/ctrl/stop.svg?v=5" alt="" />
          <span className="ft">{busy === 'stop' ? '停止中' : '停止'}</span>
        </button>
```

`onStop` 直通 `App.tsx:386` 的 `onStop={() => void stop()}`。

停止的代价不是"少跑一会儿"：`dashboard.py:261` 起的 `scheduler_stop()` 是
SIGINT 优雅退出 → 12 秒不退再 SIGTERM/SIGKILL。
`AGENTS.md` 的调度器章节写明，**重启会丢掉内存里的 pending**（"正在上课"的登记），
只能靠下次启动的 `_startup_activity_probe()` 出门实测重新发现。
而 `src/queue_status.py` 的 `mark_stopped()` 会把队列状态写成 stopped。
**误触一次的代价 = 一次出门实测 + 十几秒空窗 + 在途 pending 的重新识别**，
而按钮就在「启动」正下方、零间距。

**3b. 两枚按钮零间距。** `web/src/styles/app.css:734-745`（现状原文）：

```css

   官方 View 树就是两段（上段 feed+shower 共用容器、下段 friend 独立）。 */
.fb-group{
  /* 材质 = :root 的 --panel-bg / --panel-blur，跟任务卡 .qpanel、底栏 .deck 同一份代码
     （原来是自己写死的 rgba(255,255,255,.55)，比那两块略透一点）。 */
  display:flex;flex-direction:column;
  background:var(--panel-bg);
  backdrop-filter:var(--panel-blur);-webkit-backdrop-filter:var(--panel-blur);
  border-radius:calc(var(--u) * 25);
  box-shadow:var(--sh-1);
  overflow:hidden;

```

注释自陈"**组内按钮无缝连成一个胶囊体**"。`.fab` 是 `50×70u`（`app.css:747`），
`border-radius:0`（`:748`），无 gap → **启动与停止上下贴死，视觉上是一颗 50×140u 的胶囊**。
`web/src/styles/app.css:763` 的 `.funcbar .fab:nth-child(3){margin-top:calc(var(--u) * 20)}`
加的 20u 只作用在**第二个 group 的第一个按钮**（`画面`），
**对启动/停止这对不生效**。

功能栏位置：`left:294u`、`top:238.8u`（`web/src/styles/app.css:721,728`），
宽 `50u`。它在拇指自然落点上，且与启动按钮共用外壳——**误触停止是设计层面就存在的风险**。

**3c. 停止后没有回退通道。** `stop()` 不改任何可撤销状态，用户点错后只能重新点启动，
而重新启动要重走一遍 `_startup_activity_probe()`（出门实测）。

### ② 修复方案

采用 **长按 800ms + 进度环**（不做二次确认弹窗）：弹窗多一次点击、且在滚动容器里
容易被 `pointercancel` 吃掉（FRONTEND_PITFALLS 第三节）；长按是移动端的成熟手势，
且**误触时物理上不可能完成**——比弹窗更硬。

#### 步骤 1：`FuncBar.tsx` 改长按

替换 `web/src/components/FuncBar.tsx:1-54` 全文：

```tsx
import { useCallback, useEffect, useRef, useState } from 'react'

/** 右功能栏（官方 x=414 y=335/405/495 各 50×70）：启动 / 停止 / 画面
 *
 *  top 由 CSS 静态给出 —— `top = 右列第三颗圆钮的底 + 两倍圆钮间距`（见 app.css 的
 *  `.funcbar`）。用户明确不要"与任务列表底端对齐"那套动态定位。
 *
 *  **停止改长按 800ms**（缺陷 3）：停止会让调度器 SIGINT 退出、丢掉内存里的 pending，
 *  下次启动要重走一次出门实测才能重新发现"正在上课"。而停止按钮就贴在启动正下方，
 *  曾经是同壳无缝胶囊、点错零成本。长按 800ms 让误触物理上不可能完成。
 *
 *  手势细节（照 Overview.tsx 的 btnScene 那套，别再自创）：
 *   - 用 `pointerdown` 起表、`pointerup` / `pointerleave` / `pointercancel` 撤表。
 *     这里**可以**用 pointer 事件：`.funcbar` 是 `.home` 里的绝对定位层，
 *     但它自己不是滚动容器、手指在其中基本不产生滚动判定；且即便发出 pointercancel,
 *     我们的 cancel 处理就是"撤销长按"，正是想要的行为。
 *   - **`onClick` 必须同时撤表**：长按完成会先触发 pointerup 再触发 click,
 *     不在 click 里再撤一次，长按成功后会有一次多余的 `onStop` 之外的副作用
 *     （旧版 btnScene 就是漏了这步，导致"短按后 500ms 又切了一次背景"）。 */
const HOLD_MS = 800

export function FuncBar({
  alive,
  busy,
  onStart,
  onStop,
  onShot,
}: {
  alive: boolean
  busy: string
  onStart: () => void
  onStop: () => void
  onShot: () => void
}) {
  const [holding, setHolding] = useState(false)
  const timer = useRef<number>()
  /** 本次手势是否已经完成长按。
   *  **必须有这个 ref**：长按成功后浏览器还会补一个 click，而 `.fab` 上没有 onClick
   *  绑定动作，看起来"吞不吞都行"——但将来若有人给 `onClick` 加上任何行为
   *  （选中态、tooltip、统计埋点），没有这道闸就会在长按后多触发一次。 */
  const fired = useRef(false)

  const clearHold = useCallback(() => {
    window.clearTimeout(timer.current)
    timer.current = undefined
    setHolding(false)
  }, [])

  // 组件卸载时撤表，防定时器泄漏后对着已卸载组件调 onStop
  useEffect(() => () => window.clearTimeout(timer.current), [])

  const stopHandlers = {
    onPointerDown: () => {
      if (!alive || busy) return          // 与 disabled 同条件，disabled 时不该起表
      fired.current = false
      setHolding(true)
      timer.current = window.setTimeout(() => {
        fired.current = true
        clearHold()
        onStop()
```

### ③ 影响面与风险

- **`Overview.tsx:110-116` 的 props 不变**（`alive/busy/onStart/onStop/onShot` 五个都在），
  `FuncBar` 的对外契约完全不动，只有内部实现与 DOM 结构变。
- **`.funcbar` 从 2 个 group 变 3 个 group**，`.fb-group:nth-child(2)` 的隐藏规则
  （`web/src/styles/app.css:1485`，在 `@media (min-aspect-ratio:360/620)` 块内，
  原文是 `.funcbar .fb-group:nth-child(2){display:none}`）**语义变了**：
  旧结构里第 2 组 = 画面组，隐藏它正是那条规则的目的（该行上方注释："功能栏的
  「画面」按钮会压住底栏——直接隐藏它"）。新结构里第 2 组 = **停止组**！
  **必须改选择器**，否则扁屏上隐藏的是停止按钮、画面按钮留着——完全反了，
  且是安全性倒退。

  替换 `web/src/styles/app.css:1485`：

  ```css
  /* ⚠️ 原为 `.funcbar .fb-group:nth-child(2){display:none}` —— 旧结构第 2 组是画面组，
  ```

  `web/src/styles/app.css` 里已有的做法改给 group 加类名，然后
  `.funcbar .fb-group.fb-shot{display:none}`（此时要同时在 `FuncBar.tsx` 的
  画面组上写 `className="fb-group fb-shot"`）。

- **长按与"点一下就想停"的用户预期**。这是取舍：本方案选择"误触不可能完成"，
  代价是停止多花 0.8 秒。**必须在按钮 `title` 里写明"长按 0.8 秒"**（已在代码里），

  如果用户觉得"三块散着不好看"，可以只调 `gap` 到 12u（下限）而不必恢复同组。

### ④ 验收标准

- **C1 · 短按不生效**：点一下停止按钮（≤200ms）→ **调度器仍在跑**
  （`curl -sS http://127.0.0.1:8787/api/data | grep -o '"alive":[a-z]*'` 为 `true`），
  且不出现 `#undoStop`。改前对照：这一步会直接停掉调度器。
- **C2 · 长按生效**：按住 800ms 后松手 → 调度器停止
  （`alive:false`）、出现 `#undoStop`。按住期间按钮显示进度环绕行、文字为「松手取消」。

- **FRONTEND_PITFALLS 第三节：iOS 手势**。本节用 pointer 事件是**有意为之**

## 缺陷 4 · 成功与失败共用同一个中性 toast

### ① 问题描述

**4a. 一个 toast 承担三种语义。** `web/src/App.tsx:465-468`：


| `App.tsx:321`（拖拽排序） | `任务顺序已保存 · 下一轮调度生效` | `` `保存失败：${r.rejected.join('、')}` `` |

| `App.tsx:323,338`（异常） | — | `` `保存失败：${String(e)}` `` |

被拒绝的字段名，1.8 秒读不完。


底栏里坐着的正是 `.drawer` 状态卡（缺陷 1 的主角）。
所以**每次保存成功/失败，都会在状态信息上盖一块黑底白字的补丁**。
`z-index:99` 让 toast 稳赢（`.deck` 是 1、`.funcbar` 是 5）。

**4d. 与缺陷 1 的叠加效应**：状态卡恰好是**用户最需要持续可见**的那块
（剩余时间、当前在做什么），而它最容易被 toast 遮住。

### ② 修复方案

两条通道，语义/位置/时长/交互全部分开：

| 通道 | 语义 | 位置 | 时长 | 交互 |
| --- | --- | --- | --- | --- |
| `#torderToast`（现有，改） | **成功** | 底部，抬到底栏之上 | **1.6s** 固定 | 不可点 |
| `#actionErr`（缺陷 2 已建） | **失败** | **顶置红色** | **≥5s**，可点重试 | 可点 |

#### 步骤 1：成功/失败分流，用一个带 `kind` 的状态替代裸字符串

替换 `web/src/App.tsx:210`：

```tsx
  /** 轻提示（#torderToast）。**只用于成功**——失败一律走 showActionErr 的红色顶置条。
   *  kind 保留是为了将来可能需要中性/警告态（如"已保存，但某字段被拒绝"），
   *  现在只有 'ok' 一种，不为了对称硬造第二种。 */
  const [orderMsg, setOrderMsg] = useState<{ text: string; kind: 'ok' } | null>(null)
  const orderTimer = useRef<number>()
  const showToast = useCallback((text: string) => {
    window.clearTimeout(orderTimer.current)
    setOrderMsg({ text, kind: 'ok' })
    // **1.6 秒**（需求值）。成功信息短、用户不需要读第二遍；
    // 失败信息的停留时长由 #actionErr 自己管（5 秒 + 可点重试），不走这条。
    orderTimer.current = window.setTimeout(() => setOrderMsg(null), 1600)
  }, [])
```

替换 `web/src/App.tsx:312-328` 的 `onReorder`：

```tsx
  const onReorder = useCallback(async (restOrder: string[]) => {
    const loopKeys = Object.keys(TASK_NAME).filter(isLoopTask)
    const full = [...loopKeys, ...restOrder.filter((k) => !loopKeys.includes(k))]
    const mains = restOrder.filter((k) => TASK_GROUP[k] === '主线')
    try {
      const r = await saveSettings({
        task_order: full.join('>'),
        main_order: mains.join('>'),
      })
      // 分流：成功走底部中性 toast；失败走顶置红条并带重试
      if (r.ok) showToast('任务顺序已保存 · 下一轮调度生效')
      else showActionErr(`保存失败：${r.rejected.join('、')}`, () => void onReorder(restOrder))
    } catch (e) {
      showActionErr(`保存失败：${e instanceof Error ? e.message : String(e)}`,
                    () => void onReorder(restOrder))
    } finally {
      reload()
    }
  }, [reload, showToast, showActionErr])
```

替换 `web/src/App.tsx:332-345` 的 `saveOne`：

```tsx
  const saveOne = useCallback(
    async (updates: Record<string, unknown>) => {
```

> ⚠️ **两个 `finally` 里的 `setTimeout(() => setOrderMsg(''), N)` 必须删掉**。
> 定时器已经由 `showToast` 统一管；留着会有两个定时器互相清空，
> 表现为"toast 一闪而过"或"该消失时不消失"。
>
> ⚠️ **依赖数组必须补全**：`onReorder` 原来只有 `[reload]`，现在要加
> `showToast` 与 `showActionErr`（两者都是 `useCallback`，引用稳定）。
> 漏加会命中 `react-hooks/exhaustive-deps`，且 `noUnusedLocals` 也不会救你。

### ③ 影响面与风险

- **`orderMsg` 的类型从 `string` 变成 `{text,kind} | null`**。
  `grep -rn "orderMsg" web/src/` 命中 `App.tsx:210`（定义）、`:321`/`:323`（旧写入）、
  `:325`/`:336`/`:338`/`:340`（旧定时器）、`:466`/`:467`（渲染）——**全在本步骤范围内**。
  渲染处已加 `?.text`，不会出现 `[object Object]`。
- **`#torderToast` 的 `bottom` 从 40u 抬到 147u**，与缺陷 3 的 `#undoStop`
  （也是 `bottom:147u`）**位置重合**。两者不会同时出现吗？**会**：
  停止调度器成功 → `#undoStop` 出现 30 秒；此时如果用户去设置页改配置 →
  保存成功 → `#torderToast` 出现。两者同帧叠加。
  **处理**：给 `#torderToast` 加 `z-index:101`（高于 `#undoStop` 的 99），
  并在验收 D6 专门构造这个场景确认视觉可接受（成功 toast 压在撤销条上方 1.6 秒）。
  若不可接受，把 `#torderToast` 的 bottom 改成 `calc(env(...) + var(--u) * 190)`
  （叠在撤销条之上）。
- **`pointer-events:none` 必须保留在 `#torderToast` 上**。它抬到 147u 后正好压在
  `.scene` 任务列表的下缘，`pointer-events:auto` 会挡死最下面几行任务的点击
  （勾选框、拖拽起手）。`#actionErr` 则相反，只在 `.on` 时开 `pointer-events`
  ——这个不对称是刻意的，理由分别写在两处 CSS 注释里。

### ④ 验收标准

- **D1 · 成功通道**：设置页改任一字段 → 底部出现黑底 toast、**左侧带绿条**、
  文案 `已保存`、**1.6 秒**后消失（用秒表或 DevTools 的 Performance 面板量）。
- **D2 · 失败通道**：制造一次失败——最简做法是 DevTools Offline 后改字段。
  期望：**顶部红色条**、文案 `保存失败：...`、**5 秒内不消失**、**可点重试**。
  **底部 toast 不出现。** 改前对照：这一步是同一个底部黑 toast、1.8 秒消失、不可点。
- **D3 · 两通道不同时出现在同一位置**：

```js
const t = document.querySelector('#torderToast').getBoundingClientRect()
const e = document.querySelector('#actionErr').getBoundingClientRect()
JSON.stringify({ tBottom: t.bottom, tTop: t.top, eTop: e.top, vh: innerHeight })
```

  期望 `t.bottom < innerHeight - 135 * u`（**toast 完全在底栏之上**）；
  `e.top < 100`（错误条贴顶）。改前 `t.bottom` 落在底栏内部。
- **D4 · 底栏不被遮挡（与缺陷 1 的联合验收）**：

```js
const d = document.querySelector('.deck').getBoundingClientRect()
const dr = document.querySelector('.drawer').getBoundingClientRect()
const t = document.querySelector('#torderToast').getBoundingClientRect()
JSON.stringify({ overlap: !(t.bottom < d.top || t.top > d.bottom),
                 drawerCovered: !(t.bottom < dr.top || t.top > dr.bottom) })
```

  期望 `overlap: false`。改前为 `true`（`bottom:40u` 落在 `135u` 高的底栏内）。
- **D5 · 三种文案全覆盖**：分别触发 `任务顺序已保存` / `已保存` / `保存失败：xxx`
  三种路径，确认前两种走底部绿条、第三种走顶部红条。
- **D6 · 与撤销条共存**（见 ③）：停止调度器（出现 `#undoStop`）→ 立刻改一个设置保存成功
  → 两条同屏，确认位置/层级可接受、撤销条仍可点。
- **D7 · 成功 toast 不吃点击**：toast 显示期间点它正下方的任务行勾选框 → 能正常勾选。
- **D8** `cd web && node node_modules/typescript/bin/tsc --noEmit` 无错。

### ⑤ 回归风险点

- **FRONTEND_PITFALLS 第二节：headless 测不准 `env(safe-area-inset-*)`**。
  `#torderToast` 与 `#undoStop` 的 `bottom` 都含 `env(safe-area-inset-bottom)`
  ——headless 里该值为 0，所以 D3/D4 只能验证"逻辑上不重叠"，
  **真机（带 Home Indicator 的 iPhone）上是否刚好压住底栏只能靠截图**。
  改完必须走一次真机确认，不要只看 headless。
- **FRONTEND_PITFALLS 第三节：滚动容器里的交互**。`#torderToast` 抬到
  `.scene` 任务列表下缘、并且 `pointer-events:none`——**这是防"吃了拖拽起手"的关键**。
  同节记录过完全同类的坑（`app.css:906-912` 的注释：任务行必须静态声明 `touch-action:none`，
  否则 iOS 会先接管触摸发 `pointercancel`）。若有人为了"toast 可点关闭"把它改成
  `pointer-events:auto`，**会立刻复现"任务列表最下面几行拖不动"**。
- **`showToast` / `showActionErr` 的定时器不清理**（同缺陷 2 的说明）。
  `App` 是根组件，实际不卸载，与现有 `leaveTimer`（`App.tsx:220`）风格一致。
- **`reload()` 仍在 `finally` 里**（这里是保存类操作，不是启停类操作）。
  保存失败后刷新数据是**对的**——用户正好想知道"后端实际存成了什么"。
  与缺陷 2 里 `start`/`stop` 的处理方式不同，**这个不一致是有意的**，
  两处注释都已写明理由。

## 实施顺序建议

四条缺陷不是平行的，存在两条**通道依赖**：

1. **先做缺陷 2**（1.5 h）。它建立 `showActionErr` 这个失败通道与 `#actionErr` 组件，
   缺陷 3 的撤销条、缺陷 4 的失败分流都要复用它。先做它，后面两条只需接线。
   顺带把 `api.ts` 的 `runnerStart/runnerStop` 契约修好——缺陷 3 的长按也依赖这个
   能返回错误的版本。
2. **再做缺陷 1**（2.5 h）。这条工时最长、风险最高（动的是整个总览页底部的布局），
   单独一轮做、单独一轮验收。核心是验收 A5（`homeExtra === 0`），
   它跟 `web/src/styles/app.css:789-791` 记录的那次事故是同一个判据。
3. **然后缺陷 4**（1.5 h）。纯接线 + CSS 位置，风险低，但**必须先确认缺陷 1 已收尾**
   ——两者都改 `.drawer` / `.deck` 附近的垂直空间，同时改会分不清是谁把谁顶下去了。
4. **最后缺陷 3**（2.5 h）。它牵动 `FuncBar` 的 DOM 结构与一条 `@media` 规则
   （`app.css:1485`），是最容易静默失败的一条（见 C6）。
   放最后是因为它需要缺陷 2 的错误通道、缺陷 4 定下的 toast 位置约定都已经稳定。

**每一轮结束都跑**：

```bash

node node_modules/typescript/bin/tsc --noEmit
node node_modules/vite/bin/vite.js build
```

（`web/FRONTEND_PITFALLS.md` 第七节的最低检查。）

`dist` 更新后浏览器侧仍需强刷；且 `HTML`/静态路由是模块级常量，
