### 根因链

```
方法论：以"复刻官方 UI + 快速试错"推进，缺少抽象层与验证闭环
  │
  ├─ 前端：用绝对定位手算坐标（299 处 calc(var(--u)*N)）复刻 1080×2412 截图
  │    ├─ 无布局系统   → 高度链脆弱 → 塌陷 3 次
  │    ├─ 无栅格       → 同组圆钮间距 16u/18u 不一致 → 只能"取 17u"平均
  │    ├─ 无基准约束   → 同一变量三种分母（360 / 480 / 853）
  │    └─ 结果：app.css 占 80% 的 fix 提交
  │
  ├─ 后端：状态无单一真源
  │    ├─ "什么算今日完成" 5 份实现
  │    ├─ 四态判定 4 份 + 消费 12 处
  │    └─ 表现层混进调度器（_write_queue_status 自己重算）
  │
  ├─ 进程间：runs/*.json 当 IPC，无 schema / 无版本 / 5 处非原子写
  │    └─ 最致命：dashboard 用**正则解析日志中文文案**反推宠物状态
  │
  └─ 验证：无 CI、无 pytest、0 单测
       └─ 每次改动只能靠"用户真机上试" → 返工
```

**关键洞察**：验证方法**已经写进文档**（`web/FRONTEND_PITFALLS.md` 第 40–52 行的同源 iframe 探针、第 104 行的断言步骤），但**全靠人工执行**。方法有了，执行靠人，人就会忘 —— 这是 45% 返工率的全部答案。

## 审查过程中的更正（含对审查者自身错误的更正）

> 这一节记录**被推翻的判断**。留着它们，是因为"看起来像缺陷"和"确实是缺陷"是两回事 —— 只有查过代码才知道。

| # | 最初的判断 | 核实后 | 谁纠正的 |
| --- | --- | --- | --- |
| 1 | `AGENTS.md` 的"宽限期 600s"与"超过 10 分钟"**自相矛盾** | **不矛盾** —— `queue_status.py:105` 是 `600`，600 秒就是 10 分钟，同一值的两种表述 | 审查者自查 |
| 2 | `vite.config.ts` 的调试配置在 **11–12 行** | 实为 **12–14 行**（注释 12 / `minify` 13 / `sourcemap` 14） | 交付链审查 |
| 3 | 验收静态资源可用 **`curl -I`** 看头 | `dashboard.py` 只实现 `do_GET`/`do_POST`（`grep` 只命中 `1688`），**HEAD 一律 501**；已统一改为 `curl -s -D - -o /dev/null` | 交付链审查 |
| 4 | `_NCT` 是**模块级常量** | 是 `do_GET` 内的**局部字典**（`dashboard.py:1569`，缩进 16 空格）—— 结论（改源码须重启）不变，理由需更正 | 交付链审查的**自我纠错** |
| 5 | `app.css` 1695 行是"冗余堆积" | **误判** —— 它 639 行注释、131 个规则块、**零重复选择器**、仅 1 处 `!important`、489 处 `var()`。真正代价是 **299 处手算坐标** | 前端架构审查 |
| 6 | 299 处手算坐标**都该 token 化** | **不是** —— 其中坐标与控件尺寸约 59 处是"复刻官方截图"的产物，抽 token 会毁掉与 `UI_TREE_OFFICIAL.md` 的可追溯性。**该动的只有约 140 处（47%）** | 前端架构审查 |
| 7 | 功能栏位置"随任务列表浮动"（从截图推断） | **错** —— `FuncBar.tsx:4` 注释明确"用户明确不要动态定位"，现为固定值 | 审查者自查（截图推断被代码推翻） |

**两条独立的教训**：

- 前三类是"**记忆快照 vs 仓库现状**"的偏差（线索过时），靠**复核**纠正 —— 这就是为什么每份文档都要求"自己 `grep` 核实，禁止照抄线索行号"。
- 第 4 类是**复述时的措辞错误**，靠**自查纪律**纠正。两类错误的来源不同，防法也不同。
- 第 5、6、7 类是"**看起来像问题**"被当成问题 —— 其中第 6 条（不是所有魔法数字都是技术债）是最有价值的一条判断，它**防止了一次大规模但无收益的重构**。

## 文档间的依赖关系

执行时注意以下依赖，避免顺序错误导致返工：

```
03（交付链）──┐
              ├──> 04（布局）──> 05（设计系统）
08（验证闭环）┘         │              │
   ▲                    │              │
   │                    ▼              ▼
   └──────────────── 06（后端拆分） 07（进程契约）
```

- **08 应最先启动**：它提供的布局断言脚本是 04 的验收工具；pytest 基建是 06/07 的安全网。**没有 08，04/06/07 的改动无法验证** —— 这正是历史返工的成因。
- **04 必须在 05 之前**：布局骨架（高度链、栅格）定下来后，设计系统的 token 才有稳定基础。
- **03 与 04 可并行**：交付链改动（构建/缓存/gzip）与布局无关。
- **02 依赖 04 的单位基准结论**：触摸目标的 u→px 换算需要先确定 `--u` 的分母。
- **06 与 07 可并行**，但 07 的「日志契约根治」与 06 的「`_write_queue_status` 收敛」有交集，需协调。

## 使用方式

1. 每份文档内部按「问题 → 修复方案 → 影响面 → 验收标准 → 回归风险」组织，可**逐条勾掉**。
2. 落地前**必须复核行号** —— 本项目代码变动频繁（单日曾达 54 次提交），文档内的行号是审查时快照。
3. 每完成一条，建议在对应文档里标注 `✅ <日期>` 与实施者，便于追踪。
4. **改完必须验证**：每份文档的「验收标准」节给了可执行步骤，不要跳过 —— 这正是历史上最大的教训。
